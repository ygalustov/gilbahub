## 1. НЕРАЗРЫВНОСТИ — читать до всего остального

Три пары, которые нельзя развести по разным сдачам. Каждая — не осторожность, а измеренная причина.

### Н1. «store() перестаёт воскрешать» ⟷ «запись переезжает на store()»
Условие координатора, 18.09. Сегодня `store()` зовёт `saveSampleRecord()` семью аргументами, восьмой
`$restorableTrashedIds` остаётся `null`, а `null` в теле означает «восстанавливать можно».
`sync()` список передаёт, `store()` — нет.
**Если развести:** по-записный `POST` переедет ровно на тот путь, где воскрешение осталось, и дефект приедет
вместе с ним. Удалённая проба вернётся от первого же повторного добавления с тем же ярлыком.

### Н2. «`rawData = payload` при восстановлении» ⟷ «снос snapshot-push»
Факт 11 плана. Сегодня восстановленные с сервера пробы лежат в сторе как `values`, и `sync()` читает только
`rawData`, поэтому push безвреден: keep-list пуст.
**Если поставить `rawData` раньше сноса push:** каждое событие начнёт перезаписывать серверный payload копией
вкладки — last-writer-wins по ВСЕМ пробам сразу, и удалённые на Data page пересоздадутся.

### Н3. «`serverId` на объекте» ⟷ «обработчики `PATCH`/`DELETE`»
`PATCH` и `DELETE` адресуются серверным `id`. `client_uid` адресом быть не может: у 27 из 147 строк его нет
(Data page шлёт `null`), а ярлычные uid («Green 1») повторяются между площадками и вкладками.
**Если развести:** обработчики окажутся без адреса и либо промолчат, либо начнут гадать по `client_uid`.

## 2. СЕРВЕР — две точки

### 2.1. `saveSampleRecord()` перестаёт воскрешать
`app/app/Http/Controllers/SampleController.php`, якорь:

```php
$sample = Sample::query()->withTrashed()->firstOrNew($attributes);
if ($sample->trashed()) {
```
(на 18.09 — около :643)

**Удаляется:** `withTrashed()` и весь блок `if ($sample->trashed()) { … $sample->restore(); }`,
вместе с параметром `$restorableTrashedIds` и его проверкой `in_array`.
**Появляется:** `Sample::query()->firstOrNew($attributes)` — совпадение среди живых обновляется,
trashed-совпадение не видно вовсе, создаётся новая живая строка. Индекс `samples_site_type_client_uid_idx`
неуникальный, две строки с одним uid допустимы.

**Смежное, проверить в том же заходе:** восьмой аргумент `$restorableTrashedIds` передаётся из `sync()`
(якорь `$restorableTrashedIds = $clearSiteData ? null : [];`). После удаления параметра этот вызов и переменная
тоже снимаются. НЕ перепутать с `SiteSummary::query()->withTrashed()->firstOrNew(` двумя сотнями строк выше —
это сводки, их поведение не меняется.

### 2.2. Тест воскрешения переворачивается
`app/tests/Feature/SiteApiTest.php`, якорь:

```php
public function test_authenticated_user_sync_does_not_restore_a_deleted_sample(): void
```

Уже утверждает «не воскрешает» для `sync`. **Появляется:** тот же случай для `store()` —
удалить через `DELETE /api/samples/{id}`, повторить `POST` с тем же uid, проверить: старая строка trashed,
новая живая, `index` показывает одну.
Исключение с `clearSiteData` описано в `Gh430SamplesNoSnapshotDeleteTest` и остаётся как есть.

### 2.3. Проверка `_turfProfile` (пункт 8 плана)
Один PHPUnit: `GET /api/samples/{id}/analyse` на пробе, у которой в `payload` лежит объектный `_turfProfile`.

### 3.2. ПОЯВЛЯЕТСЯ: восстановление несёт `serverId` и разделяет payload
Якорь точки правки:

```js
serverSnap.allSites[siteId][sample.sample_type][sampleId] = {
```
(на 18.09 — около :430; объект заканчивается на `soilTextureSnapshot:  sample.soil_texture_snapshot || null`)

**Добавляется в объект:**
- `serverId: sample.id` — адрес записи;

  (`const row = sample.rawData || sample.values || null;`). Убирается в стадии 3, не здесь.

### 3.3. ПОЯВЛЯЕТСЯ: шесть по-записных обработчиков
Вместо одного `scheduleSave` — по обработчику на событие. Таблица тел — раздел «Стадия 2, п. 4» плана,
**с четырьмя поправками раздела устройства (B.2), они обязательны:**

1. **Площадка — из записи, не из указателя.** Тело берёт `siteId` из `event.detail`, НЕ из
   `SM.getActiveSiteId()` (якорь `getActiveSiteId: function() { return _currentSite; }`). Проба, добавленная за
   миг до переключения, иначе уйдёт на другую площадку — класс GH-459.
2. **События несут то, что нужно запросу.** Добавить `siteId` во все; `serverIds` — в оба clear-события,
   снятые ДО очистки стора.
3. **`gaip:sample-turf-profile-changed` добавляется** в список (сегодня его там нет).
4. **`gaip:site-changed` из списка убирается** — переключение не изменение данных, ноль запросов.

**Очередь по записи:** операции над одной записью — цепочка обещаний; `PATCH`/`DELETE` ждут `201` от `POST`
(иначе нет `serverId`). Над разными записями — независимы.

**Отказ виден:** не 2xx или сеть → `sample._dirty = {op, error}` и событие
`gaip:samples-persistence-error {sampleId, op, status}`; объект из стора НЕ удаляется. 403 и 419 — свои
сообщения. Маркер и Retry в интерфейсе — стадия 3.

**Миграция как источник событий, ловушка:** `gaip:sample-updated` шлётся и миграцией с
`reason: 'b35fix411-migration'`. Обработчик обязан пропускать события с `reason`, иначе загрузка страницы даст
N лишних `PATCH`.

### 3.4. `MUTATION_EVENTS` — что с ним

## 6. ПОРЯДОК ВНУТРИ СДАЧИ

Порядок выбран так, чтобы **площадка ни в один момент не отвечала двумя способами**: пока push жив, по-записных
запросов быть не должно, и наоборот.

1. **Сервер:** снять воскрешение (2.1) + переписать тест (2.2). Дерево остаётся рабочим: push ещё жив,
   «не воскрешать» пока означает «создать новую строку с тем же uid».
2. **Клиент, восстановление:** `serverId` + разделение payload (3.2). Поведение не меняется —
   `rawData` появляется, но push ещё читает его… **СТОП: здесь Н2.** Шаги 2 и 3 **неразрывны**, между ними
   дерево некорректно: `rawData` заполнен, push жив, каждое событие перезапишет всё.
3. **Клиент, запись:** снос раздела записи (3.1) + шесть обработчиков (3.3) + `detail` в `sample-manager` (4)
   — **одним движением с шагом 2**.
4. **Права** (5) — после того как запись работает, до живого прогона.
5. **Тесты:** Jest-набор раздела 10 (add→POST, update→PATCH с ПОЛНЫМ payload, delete→DELETE,
   clear→N×DELETE, turf-profile→PATCH, site-changed→ноль, guard «ни одно тело не содержит `allSites`»,
   `canEditActiveSite:false`→ноль) + PHPUnit 2.3.
6. **Приёмка:** контрольный прогон обоих наборов зелёный, потом мутация ревьюера.

**Шаги 2+3 — единственный участок, где дерево заведомо некорректно.** Его нельзя прерывать. Всё остальное
можно останавливать между пунктами.

## 8. ЧЕМ ПРОВЕРЯЕТСЯ (раздел D плана, сжато)

- **Журнал запросов:** за сессию с N действиями — ровно N запросов к `/api/samples*`, каждый с одним
  `serverId`; `gaip:site-changed` — ноль. Ни одно тело не содержит `allSites`.
- **Четыре точки по базе** до и после каждого действия: add → +1 живая строка с `site_id` ЗАПИСИ;
  update → тот же `id`, payload целиком (фикстура с ключом `thatch`), штампы не изменились;
  delete → `deleted_at` и `delete_source`; повторный POST после удаления → новая строка, старая trashed.
- **Площадка из записи:** добавить пробу, переключить площадку до ответа (`route.delay`), проверить `site_id`.
- **Живой прогон:** площадку, пробу и ожидание назвать ДО; снимок стенда до и после.
  **Запрет в силе:** четырнадцать живых тестов без средства защиты не запускаются — если понадобится один из
  них, сначала средство. Три худших: `gh459-cross-site-inputs-live`, `gh404-settings-location-required-live`,
  `gh526-stage1-routes-live`.

## 10. ЗАКРЫТИЕ РАЗДЕЛА 9 — дописано при реализации (GH-533, 18.09)

Все четыре пункта замерены до первой правки. Замеры, а не рассуждения:

1. **`bindAutoSave` в `hub-persistence.js` — к пробам отношения не имеет.** Цепочка
   `bindAutoSave` → `scheduleSave` → `saveImmediate` → `save` пишет в localStorage и зовёт
   `syncToServer(cache)`, а тот шлёт **analysis_cache**, не пробы. Точка правки стадии 2 на неё не опирается.
2. **`PATCH` действительно перезаписал бы `client_uid`** — `SampleController::update()` его валидирует и
   присваивает. Решение принято на стороне клиента: `client_uid` в теле `PATCH` **не шлётся**, серверная
   валидация не тронута. Иначе переименование сдвигало бы ключ повторного импорта.
3. **У `addSample` другого источника площадки нет** — только `_currentSite`. Поэтому `siteId` кладётся в
   `detail` в момент действия, а обработчик берёт оттуда.
4. **Кнопок в `sample-switcher-ui.js` — не пять, а восемь поверхностей правки:** пять в шапке
   (Import / Save / Rename / Set area / Set turf profile), плюс шестерёнка, плюс контекстное меню по
   правой кнопке, плюс переименование двойным кликом. Закрыты все восемь одним `canEditSamples()`.
