## Что именно установлено, по полям

### Имя → ID (установлено, сценарий E)

`sample-persistence.js` строит регистр сайтов так:

- `fetchSiteListFromServer()` — берёт имена из `GET /api/sites`. Если запрос упал, регистр остаётся пустым.
- `fetchSamplesFromServer()` — для каждого сайта, которого нет в регистре, ставит `label = (sample.summary && sample.summary.site_name) || siteId` (строка ~389). Но `SampleController::samplePayload()` **не отдаёт `summary`** (строки 518-535) — значит ярлык всегда `= siteId`.
- Дальше `SM.setActiveSite()` → `gaip:site-changed` → `doSave()` → `syncSiteListToServer(snapshot.sites)` без какой-либо проверки ярлыка → `syncRegistry()` для существующего сайта делает `update(['name' => $name])`, где `$name = ID` (проверка только на `''` и на префикс `__site__`).

Живой результат (прогон 2, E): страница `/analysis` при `GET /api/sites` → 500 отправила
`POST /api/sites/sync` с ярлыками-ID для **всех десяти** сайтов логина, где есть пробы; в базе `sites.name` скретч-сайта стал `01a0a200-18a2-70d7-8bd7-2561d58a21de`. Остальные девять не пострадали только потому, что тест переписывал тело запроса и оставлял в нём один скретч-сайт.

Важно: тот же ярлык `= ID` появился в H1 при **медленном**, а не упавшем `GET /api/sites` (7 с задержки): второй `POST /api/sites/sync` со страницы `/reports/forensic` нёс `"01a0a200…": {"label": "01a0a200…"}`. Так что условие — не «сервер лежит», а «список сайтов пришёл позже, чем регистр понадобился».

Для не-админа до GH-359 `GET /api/sites` возвращал 500 **всегда** (`wherePivot('status')` по несуществующей колонке). Клиент — не админ. Нужно проверить на проде, что развёрнутая сборка содержит GH-359; если нет — это и есть первый эпизод, и он повторится при каждом открытии `/analysis` любым не-админом.

Лид из брифа «`syncRegistry()` и есть подпись» — верен наполовину: `syncRegistry()` — исполнитель, но сам он имя не выдумывает; ID ему присылает `sample-persistence.js`. Гвард `label === siteId ? ''` есть только в `site-config-persistence.js` (`syncSiteRegistryToServer`), во второй копии этого кода в `sample-persistence.js` его нет.

### Конфиг целиком / мастер настройки (установлено, сценарий H1)

Hub-страницы грузят `site-config-persistence.js`, который держит копию конфигов **всех** сайтов в `localStorage` (`gilba_hub_site_configs`) и по любому поводу (`saveCurrentSiteConfig()` при `gaip:site-changed`, `mergeConfig()`, companion species, multi-site toggle) вызывает `pushConfigsToServer()` — тот делает `PUT …/config/gaip` **для каждого** сайта из локальной копии. Сервер (`SiteController::updateConfig()`) заменяет колонку `config` целиком; защищены только три программных ключа (`resolveGaipConfigWrite()`, GH-371).

Откуда берётся пустая копия: в `init()` таймер «восстановления» ставится на 3000 мс, если локальной копии активного сайта нет (`restoreDelay`), и если `pullConfigsFromServer()` за это время не ответил, ветка «first visit» через ещё 600 мс делает `snapshotConfig()` с DOM (`.gaip-species`, `.gaip-soil-methodology`, `.gaip-n-program` и т. д. — умолчания легаси-разметки) и сохраняет как конфиг сайта. Ключа `wizard` в снимке нет вообще (`snapshotConfig()` возвращает `turf|location|pgr|multiSiteTurf|savedAt` + перенос программ). `savedAt` у снимка свежий, поэтому пришедший позже ответ сервера идентичные поля уже не перекрывает (`pullConfigsFromServer()` перекрывает только identity-поля и только если сервер новее).

Живой результат (прогон 2, H1): `/reports/forensic`, `GET /api/sites` задержан на 7 с. Страница сделала **14 `PUT …/config/gaip`** — по одному на каждый сайт логина (включая все 12 реальных dev-сайтов). Для активного скретч-сайта до: `keys=pgr|turf|wizard|savedAt|location|…`, `nProgram: 200`; после: **`wizard` отсутствует**, `nProgram: "250"` (DOM-умолчание поля Annual N). Вид и методология уцелели только потому, что DOM-умолчания легаси-формы — Perennial Ryegrass, а `ammonium-acetate-methodology.js` сам переключает селект на AA по NZ-координатам; для сайта с бентграссом/MLSN снимок принёс бы Perennial Ryegrass и SLAN (первая опция селекта `.gaip-soil-methodology`).

Именно это делает мастер «брендново́го» сайта: на `/hub` и Reports-страницах `site-setup-wizard.js` показывается, когда `GAIP_WIZARD_CONFIG.wizardComplete` (= `config.wizard.complete`) ложно; на дашборде `onboarding-wizard.js` — когда нет `turfSpecies`, `turfMethodology` или координат сайта. После H1-записи `wizard` нет → мастер.

Побочно H1 создал через `sites/sync` новый сайт `my_site` («My Site») — легаси-миграция ключа `default` в `site-config-persistence.js` (`migrateDefaultSite`). Ещё один путь, которым в базе появляются «чужие» сайты.

Сценарий H2 (старая локальная копия сайта в браузере, открыта hub-страница на другом сайте) — конфиг остался цел, но за 25 с не наблюдалось ни одного `PUT`, поэтому он **не подтверждает и не опровергает** перезапись «чужого» сайта; по коду `pushConfigsToServer()` шлёт все ключи, и в H1 это видно на 14 запросах.

### Методология AA → SLAN после Generate (установлено, сценарий B)

`plan.blade.php` рендерит `window.GAIP_SITE_CONFIG = @json($gaipConfig)` при загрузке; `persistSiteConfigPatch()` на странице Plan (там нет `GAIP_SiteConfig`) делает `Object.assign(GAIP_SITE_CONFIG, patch)` и `PUT` всего объекта. Живой результат: база `slan` → открыта вкладка Plan (`GAIP_SITE_CONFIG.turf.methodology = slan`) → в Settings сохранено `ammonium_acetate` (в базе AA, проверено) → Generate во вкладке Plan → три `PUT` с `turf.methodology = slan` → в базе снова `slan`. Тот же поток в одной вкладке (Settings → переход на Plan → Generate, сценарий C) — корректен, AA сохраняется. То есть «поставил AA, перегенерировал — вернулось SLAN» требует лишь ранее открытой вкладки Plan — или второго человека с открытым Plan.

Отсюда же: Plan возвращает и `location` из старой копии, а `resolveGaipConfigWrite()` синхронизирует `location.lat/lon` обратно в строку `sites` — старая вкладка Plan способна откатить и координаты сайта.

### Локация «Сидней» / «Австралия» (не воспроизведено как запись в базу)

Ни один из сценариев не записал сиднейские координаты. Что установлено:

- Строка сайта, созданная `syncRegistry()` (сценарий F), имеет `timezone = Australia/Sydney`, `latitude/longitude = NULL`, пустой конфиг. Оба мастера при `POST /api/sites` тоже шлют `timezone: 'Australia/Sydney'` (`onboarding-wizard.js:602`, `site-setup-wizard.js:1218`), в том числе для NZ-сайтов.
- Settings > Site: селект `#stg-timezone` при `timezone = NULL` показывает первую опцию «Australia — Sydney / Melbourne» (нет пустого варианта), и сохранение формы запишет её.
- Без координат hub-модули подставляют -33.87 (вопрос 13 плана) — расчёт «для Сиднея», но в `sites` это не пишется.

Самое вероятное чтение: владелица видела либо селект таймзоны, либо результат расчёта на подставной широте после того, как координаты в её копии/на странице отсутствовали. Что из этого — проверяется по проду: `SELECT latitude, longitude, timezone, created_at FROM sites WHERE id = '<ID из скриншота>'`. Если `created_at` совпадает с инцидентом и `name = id` — это сценарий F (в localStorage у кого-то был ID, которого не было в базе; в скриншоте ID `019e1b2-…` с семизначной первой группой — если это не опечатка, база его никогда не знала).

### Пропавшая почвенная информация (не расследовалось глубоко)

Кандидаты: (а) сайт-двойник из сценария F — у него проб нет; (б) `POST /api/samples/sync` до GH-430 мягко удалял пробы, которых нет в снимке браузера (вопрос 1 плана, воспроизведено 10.09) — «после Re-run проба вернулась» совпадает с тем, что легаси-страница снова прислала её из localStorage. Проверка на проде: `SELECT id, deleted_at FROM samples WHERE site_id = '<ID>'`.

### Re-run (сценарий D) — не пишет конфиг

Кнопка Re-run (`dashboard-ui.js`) грузит `/hub` в скрытом iframe. Из iframe уходят только `POST /api/analysis-cache` и `POST /api/samples/sync`; `pushConfigsToServer()` и `syncSiteListToServer()` в iframe заблокированы гвардами. Строка `sites` и конфиг до/после — идентичны. Лид «Re-run переписывает конфиг» — **отброшен**. Но Re-run стемпит `gilba_samples.currentSite` в localStorage, а после завершения перезагружает страницу — и следующая загрузка `/analysis` идёт по путям из сценария E.

Лид «две базы (кэш анализа и конфиг) расходятся» — в этой части не подтверждён: `analysis_cache` хранит только `metrics/computed`; топбар и дашборд читают методологию из `gaip.turf.methodology` (`AppServiceProvider`, `DashboardController::effectiveMethodology()`), а не из кэша. Расхождение «Plan показывает AA, дашборд — SLAN» объясняется тем, что Plan-вкладка была отрендерена до перезаписи, а дашборд — после.

## План исправления (порядок важен)

### 1. Серверный гвард в `SiteController::updateConfig()` — ставить первым, закрывает все пути сразу

Сейчас `config: ['present','array']` принимает что угодно, в том числе `[]`. Предлагаемая семантика (решение продукта, моя рекомендация — вариант А):

- **А (рекомендую). Слияние вместо замены.** Верхнеуровневые ключи, отсутствующие в запросе, переносятся из текущей строки (расширение того, что `resolveGaipConfigWrite()` уже делает для трёх программных ключей, на все ключи). Внутри `turf` и `location` — то же на уровне полей: пустая строка/`null` в запросе не затирает непустое значение в базе. Явное стирание — только через отдельный флаг в теле (`"clear": ["pgr"]`) или отдельный маршрут. `wizard` никогда не удаляется PUT-ом без флага.
- **Б. Отказ (422) вместо тихой правки**: если запрос обнуляет `turf.species`, `turf.methodology`, `location.lat/lon` или убирает `wizard` при непустом текущем значении — 422 с перечнем полей. Проще в реализации, но hub-страницы получат 422 на каждом фоновом пуше и будут писать `warn` в консоль — приемлемо как временная мера.

В обоих вариантах: писать `Log::warning` с `site_id`, `user_id`, `referer` и списком «затираемых» полей — это и есть след для следующего инцидента.

Проверка: PHPUnit в `app/tests/Feature/` — PUT со снимком без `wizard` и с `turf.nProgram = "250"` при полном конфиге в базе → `wizard` на месте, `nProgram` не изменился (вариант А) или 422 (вариант Б); PUT с пустым `config` → строка не изменилась. Red-check: убрать гвард → тест падает; E2E-сценарий H1 снова теряет `wizard`.

### 2. `syncRegistry()` — не принимать ID как имя и не создавать сайты молча

- `if ($name === $siteId || preg_match(UUID)) $name = ''` — тогда существующий сайт сохраняет имя (ветка `$name !== '' ? $name : $site->name` уже есть).
- Создание строки для неизвестного ID — либо убрать, либо требовать явный `create: true`; сейчас это единственное место, где сайт рождается без координат, с `Australia/Sydney` и пустым конфигом (и падает 500 на мягко удалённом ID — сценарий F, прогон 2).
- Клиент: в `sample-persistence.js` `syncSiteListToServer()` добавить тот же гвард `label === id ? ''`, что есть в `site-config-persistence.js`; лучше — вообще не слать ярлыки из легаси-регистра, имя живёт в `sites.name`.

PHPUnit: `POST /api/sites/sync` с `label = id` для существующего сайта → имя не меняется (существующий `test_authenticated_user_can_sync_legacy_site_registry_ids` проверяет только создание с нормальным ярлыком — поэтому и прошёл).

### 3. `site-config-persistence.js` — перестать пушить всё и перестать пушить снимки

- `pushConfigsToServer()` шлёт только активный сайт, и только если для него уже завершился `pullConfigsFromServer()` (флаг «сервер прочитан»); ветка «first visit» (`Captured initial config … (first visit)`) сохраняет в localStorage, но **не** становится основанием для PUT.
- `pullConfigsFromServer()` при существующей локальной копии переносить **все** ключи сервера, а не только identity-поля и программы (иначе локальная копия навсегда без `wizard`/`location`/`nProgram`).
- `migrateDefaultSite` не должен создавать `my_site` на сервере.

Проверка: сценарий H1 — ноль `PUT` для неактивных сайтов, `wizard` и `nProgram` на месте.

### 4. Plan и Settings — патч вместо копии страницы

- `persistSiteConfigPatch()` на Plan: слать только патч (`nutritionCalendarProgram`, `nutritionProgram`, `maxNPerMonth`, `appliedMonthlyN`, `nzDistributor`, stamp) на merge-endpoint из п. 1, а не `GAIP_SITE_CONFIG` целиком. Это закрывает сценарий B без каких-либо блокировок вкладок.
- Три формы Settings (вопрос 6 плана) — то же: слать только свои секции.

Проверка: сценарий B зелёный; red-check — вернуть PUT целиком → B красный.

### 5. После 1–4 — снять с dev `GAIP_HUB_CONFIG`-зависимость мастера от `wizard`: если `turf.species` и координаты есть, мастер не показывать даже без `wizard` (мягкая защита от уже испорченных строк).

## Почему тесты это пропустили

- `SiteApiTest::test_authenticated_user_can_sync_legacy_site_registry_ids` проверяет создание сайта с человеческим ярлыком, не проверяет ни `label = id`, ни существующий сайт.
- `GH371CoordinateInvalidationTest` проверяет только три программных ключа в `updateConfig()`; замену остальных ключей никто не пиннит — она считалась нормой.
- `tests/gh377-…`, `gh371-…`, `gh385-…` — jsdom-тесты `snapshotConfig()`/`restoreConfig()`; сеть и таймер 3000 мс в них не участвуют, поэтому ветка «first visit + медленный pull + push всех сайтов» не покрыта ни одним тестом.
- E2E-харнессы работают под админом на быстром локальном стенде: `GET /api/sites` никогда не падает и не опаздывает, `label = id` не возникает.

Файл `gh439-config-reset-live.test.js` оставлен как красная проверка: сценарии B, E, H1 должны стать зелёными после пп. 1–4; F после п. 2 нужно переписать на «сайт не создан». F в прогоне 2 упал по артефакту (мягко удалённая строка с тем же ID от прогона 1 → 500 `Duplicate entry`) — это отдельное наблюдение, не дефект теста логики.

## Ответы на два вопроса владельца (добавлено 15.09.2026)

### 1. Одна корневая причина

Корень один: у конфигурации сайта два «истинных» представления — строка в базе и **копия целого объекта в браузере** (`gilba_hub_site_configs` в localStorage, `window.GAIP_SITE_CONFIG` на Plan, `D.gaipConfig` на Settings, легаси-регистр сайтов в `gilba_samples`), а сервер (`PUT …/config/gaip`, `POST /api/sites/sync`) принимает от любой из этих копий **состояние целиком** («вот объект, замени»), не зная, читала ли копия текущую базу и когда. Четыре пути — не четыре независимых дефекта, а четыре поверхности одного и того же выбора «состояние принадлежит клиенту, сервер хранит blob»: H1 — снимок с DOM отправлен как состояние всех сайтов; B — копия на момент загрузки вкладки отправлена как состояние; E/F — построенный клиентом ярлык отправлен как имя. Различаются только моменты срабатывания (медленный pull, старая вкладка, упавший список сайтов) — сама возможность записи «как есть» общая. Если бы сервер принимал только намерение («методология = AA», «программа сгенерирована для таких входов», «мастер завершён») и никогда — объект, пути 1, 2 и 4 были бы невозможны, а путь 3 не был бы записью вообще (у клиента не было бы права присылать имя). Это же семейство породило GH-371, GH-377, GH-385, вопрос 6 плана и вопрос 1 (пробы) — шесть инцидентов за месяц из одного решения.

### 2. Системно или по путям

**Да, та же логика, что в `PLAN-samples-sync-FINAL.md`, применима — и к конфигурации даже лучше, чем к пробам.** Объект маленький (одна JSON-строка на сайт), писателей всего ~13 вызовов в 6 файлах, офлайна нет и не было, и сервер уже рендерит конфиг в каждую db-shell страницу (Plan, Settings, Dashboard, Analysis читают из базы, а не из копии). Единственное содержательное отличие от проб: у конфига есть законный **клиентски вычисляемый** продукт — программа питания (`nutritionCalendarProgram`/`nutritionProgram`), которую считает браузер и кладёт в тот же объект. Это остаётся клиентской записью, но как намерение «программа сгенерирована для координат X, вида Y, методологии Z» (штамп уже есть — GH-371/GH-377), а не как «вот весь конфиг». У проб такого продукта нет, поэтому там копию можно убрать полностью; здесь — оставить как кэш чтения.

**Что нужно, чтобы браузер вообще не пушил конфигурацию (честный размер):**

- Сервер: `PATCH /api/sites/{id}/config/gaip` с глубоким слиянием по секциям (`turf`, `location`, `pgr`, `traffic`, `irrigation`, `weatherOverride`, `wizard`, программные ключи со штампом), явное стирание отдельным маршрутом/флагом, PUT-замена убирается; `sites/sync` перестаёт принимать ярлыки и создавать сайты (имя редактируется только в Settings через `PATCH /api/sites/{id}`). Вместе с PHPUnit — 2–3 дня.
- Клиент, писатели (все переводятся на PATCH-намерения): `nutrition-calendar.js` `persistSiteConfigPatch()` (уже патч по форме — самый простой), `settings-init.js` (3 формы + импорт + traffic), `onboarding-wizard.js` `_persist`, `site-setup-wizard.js` `persistWizardState`, `site-config-persistence.js` (`pushConfigsToServer`, `mergeConfig`, `setCompanionSpecies`, `setMultiSiteTurfEnabled`, `saveCurrentSiteConfig`, ветка «first visit»), `sample-persistence.js` `syncSiteListToServer` (удаляется). Основной объём — `site-config-persistence.js` (~1900 строк): вся его модель — «снимок DOM → localStorage → push». Правки легаси-полей на `/hub` (вид, HOC, методология в старой форме) при этом перестают быть источником записи вовсе; это согласуется с правилом проекта «новый хаб полностью заменяет старый»: старый хаб становится читателем. 4–6 дней, плюс переработка jsdom-тестов, запиненных на `snapshotConfig()`/`restoreConfig()` (gh371, gh377, gh385, b35fix504 — порядка сотни тестов), плюс 2 дня живой проверки. Итого ≈ 2 недели одного разработчика против 3–4 дней на гвард + четыре точечные правки.

**Что ломается, если локальная копия исчезает как источник — и что из этого настоящее требование:**

- Переключение сайта на `/hub` без перезагрузки и восстановление легаси-DOM из конфига (`restoreConfig`) — читатель; работает с кэшем, наполненным с сервера. Требование настоящее (скрытый раннер экспорта переключает сайты).
- Комбинированный Word-экспорт читает конфиги **других** сайтов (`word-export.js`, `word-export-combined.js` через `GAIP_SiteConfig.getConfig()`) — читатель; тот же кэш с сервера (`GET /api/sites` уже отдаёт все конфиги). Настоящее.
- Ещё 12 файлов-читателей (`daily-dashboard.js`, `hub-orchestrator.js`, `climate-normals-service.js`, `gilba-alerts.js`, `gaip-morning-briefing.js`, `nutrition-*-integration.js`, `site-setup-wizard.js` и др.) — все `getConfig()`, ни один не пишет. Настоящие, но им безразлично, откуда кэш.
- Зеркало Settings в localStorage (`settings-init.js` пишет `gilba_hub_site_configs`, «чтобы hub-страницы увидели новое значение») — привычка, компенсирующая то, что hub-страницы не перечитывают сервер; с серверным кэшем не нужна.
- «Первый визит» и 3-секундный `restoreDelay` — не требование, а гонка; исчезает.
- Работа при недоступном сервере — не требование (офлайн не поддерживается, то же решение, что по пробам).
- Легаси профили TPC (`gilba_turf_profiles`, `site-profile-bridge.js`) — уже решено не переносить (Profile Save/Load → мульти-сайт).

**Середина, которая не фадж:** API `GAIP_SiteConfig` (`getConfig`, `getAllConfigs`, `restore`) остаётся, меняется его начинка: кэш только чтения, наполняется один раз из `GET /api/sites` при загрузке (для Reports-страниц ещё и инжект `gaipConfig` в `GAIP_HUB_CONFIG`, как это уже сделано для `/hub` в `layouts/app.blade.php`), обновляется локально только **после** успешного PATCH-намерения на сервер; `snapshotConfig()` перестаёт быть источником записи, `pushConfigsToServer()` удаляется. Инвариант, который нужно закрепить, — не «в браузере ничего не хранится», а **«браузер никогда не пишет состояние, только намерение»**: копия для чтения и hub-раннеру, и экспорту нужна.

**Где я не согласна с постановкой:** гвард плюс четыре точечные правки действительно закрывают *этот* дефект, и делать их нужно первыми — это дни, а не недели. Но они оставляют на месте: фоновые 14 `PUT` на загрузку страницы (при варианте Б — 14 тихих 422 в консоли); неразрешимую двусмысленность «чья копия права» для легитимно изменённых полей (старая вкладка Plan всё ещё пришлёт старый `location.name`/`pgr`, и слияние либо их примет, либо запретит Settings когда-либо очищать поле); и сам механизм, который уже дал шесть инцидентов. Поэтому системный путь — не «стоимость без пользы», а единственный, после которого следующий такой отчёт не понадобится. Рекомендация: **стадиями, как у проб** — стадия 0: серверный гвард/слияние (самостоятельна, ставится первой, закрывает кровотечение); стадия 1: PATCH-намерения + перевод Plan и Settings (закрывает сценарий B без «блокировок вкладок»); стадия 2: `site-config-persistence.js` становится кэшем чтения, push и синхронизация ярлыков удаляются (закрывает H1 и E); стадия 3: localStorage-копия удаляется, `GAIP_SiteConfig` живёт в памяти страницы. Каждая стадия проверяется тем же `gh439-config-reset-live.test.js`.
