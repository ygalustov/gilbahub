## Есть ли у нас устройство журналирования — нет, для документов

- **Выгрузку собирает браузер.** Сервер о ней не знает ничего: в `app/routes/web.php` нет ни одного маршрута записи для экспорта. Таблиц выгрузок нет — `SHOW TABLES` по `export` пусто, по `log` только `field_log_entries` и `spray_logs` (журналы площадки).
- **Серверный журнал Laravel** — файл (`LOG_CHANNEL=stack`, `LOG_STACK=single`), 8 вызовов `Log::…` в `app/`. В базе его нет, выгрузки туда не пишут. Для вопроса «сколько раз» не годится: не запрашивается, ротируется, и браузер туда не пишет.
- **Есть журналы соседнего рода — образец, не место:**
  - **прогоны** — строка результата с исходом и причиной (`analysis_results`, `outcome`, `reason`). Браузер сообщает провал через `storeRun` (`AnalysisCacheController.php`, якорь `public function storeRun(Request $request): JsonResponse`) → `AnalysisResults::recordFailure`;
  - **прогнозы** — `/predictions`, `/outcomes`.

  Приём `storeRun` — браузер сообщает серверу факт, который он наблюдал, сервер хранит — это и есть образец.

## Чего не узнать сегодня и после — точно

- **До сдачи 3гу — ничего.** Пропуск пробы не пишется никуда, кроме консоли. Строки `failed` показывают упавшие прогоны, но не то, шли ли они внутри выгрузки. Восстановить прошлое нечем. **Это «следа нет», а не «пропусков не было».**
- **После сдачи — вперёд, и только то, что сервер получил** (граница ниже).

## Что писать

**Одна запись на один документ**, и одиночный, и объединённый. «Документ без раздела» бывает двух видов, и оба в записи:
1. **Проба не вошла** (объединённая выгрузка, 3гт): площадка, проба, код причины — прогон не состоялся, не уложился во время, конфиг не применён — и `run_id` прогона, которого ждали. По `run_id` запись связывается со строкой `failed`, если она есть.
2. **Раздел не вошёл внутри отчёта** — реестр `GH-488`, который Word уже ведёт по каждому отчёту (`data.availability`: поле, исход `empty` / `unavailable` / `omitted`, причина). Записывается как есть, без пересказа.

Плюс шапка документа: кто, для какой учётной записи, одиночный или объединённый, какие пробы выбраны, сколько вошло.

**Коды причин — один источник.** Коды и тексты причин живут в реестре Word (`SCOPE_RULES`, `REASON_TEXT`, три новых кода из 3гт). Сервер хранит код строкой, **своего перечня не заводит** — правило «один файл, один читатель». Группировка по коду — на чтении.

## Куда

**Новая таблица `document_exports`:** `id`, `user_id`, `account_id`, `kind`, `started_at`, `finished_at`, `outcome`, `selected` (JSON), `included` (JSON), `skipped` (JSON — проба, площадка, код, `run_id`), `not_included` (JSON — записи реестра `GH-488` по отчётам).

Хранилище на сервере со своим владельцем — цель правила проекта, а не нарушение. Браузер отправляет **факт о документе, который он собрал**, а не копию состояния страницы. Это тот же род, что `storeRun`.

## В какой момент — два, а не один

1. **В начале выгрузки** — `POST`: вид и выбранные пробы. Ответ — `id` записи. `outcome = started`.
2. **В конце** — `PATCH` по `id`: вошедшие, пропущенные с кодами, записи реестра, `outcome` — `completed`, `cancelled` (кнопка отмены окна хода, якорь `progress.isCancelled()`) или `failed` (якорь `progress.error('Export failed: ' + err.message)`).

**Почему два.** Запись только в конце теряет ровно те случаи, где что-то пошло не так: закрытая вкладка, упавшая сборка. С двумя моментами запись без конца остаётся `started`. Это отвечаемый исход «выгрузка не завершилась», а не пустота.

**Документ журналом не держится.** Если запрос журнала не прошёл, выгрузка идёт дальше, и клиент получает документ. Провал журнала — одна строка в консоли. Блокировать клиента из-за нашего счёта — не то, что просили.

## Как отвечать «сколько раз»

Консольная команда по требованию, образец — `gilba:audit-data` (`app/Console/Commands/AuditData.php`). Печатает:
- выгрузок всего, по видам и исходам;
- проб пропущено, по кодам причин;
- документов с хотя бы одной строкой «Not included», по полям и исходам.

Всё перечнем, а не только числом, — правило про сторожей. Экрана для этого не делается: его не просили.

## Граница — названа

- **Журнал знает только то, что сервер получил.** Выгрузка, чей первый запрос не дошёл, в журнале не существует. Запросы на стенде ходят к тому же серверу, что и остальная страница, но частоту таких провалов не измерить изнутри самого журнала.
- **Прошлое не восстанавливается.** До сдачи — только строки `failed`, и без привязки к выгрузкам.
- **Одиночный экспорт пробы не пропускает**, у него только записи реестра `GH-488`.

## Порядок и пересечения

- **После 3гт.** Коды причин пропуска и сами ворота появляются там. Журнал записывает их исходы. Без 3гт пропусков, кроме `GH-498`, нет, а чужая площадка печатается молча — журнал записал бы «вошло» там, где вошло чужое.
- **С `GH-488`** — читает его реестр, не меняет.
- **С 14:** живой экспорт пишет строки. Проверка живым прогоном — в окне пункта 14.

## Браузерные копии в этой области

Нет новых. Браузер отправляет факт о собранном документе и ничего не хранит для записи обратно. Искала — `localStorage` в двух файлах экспорта для этой цели не используется.

## Проверка

- **PHP:** `POST` создаёт запись `started`; `PATCH` своей записи ставит исход и перечни; чужую запись — отказ. Запись без `PATCH` остаётся `started`. Команда печатает перечень по кодам.
- **JS, стенд цикла объединённой выгрузки** (тот же, что в 3гт): одна проба пропущена с `calculation-error` → тело `PATCH` несёт её с кодом и `run_id`. Отмена → `cancelled`. Журнал не отвечает → документ всё равно собирается.
- **Положительный контроль и мутацию выбирает ревьюер.** Кандидат — не отправлять `skipped`: случай обязан назвать пробу, которой нет в записи.

## Признак сдачи — числом

- Выгрузок, после которых нельзя сказать, какие пробы не вошли и почему: все → 0 (для дошедших до сервера).
- Устройств, отвечающих на «сколько раз», — 0 → 1 (команда).
