## 0. Обобщение: как тест перестаёт сторожить

Восемь случаев Вопроса 26 и девять из GH-436 сводятся к шести способам. Каждый способ даёт признак для механического
поиска (раздел 1) и свою мутацию для красной проверки (раздел 2). Классификация — рабочий инструмент прохода: у каждого
кандидата в реестре стоит буква.

| Буква | Способ | Случаи | Почему зелёный |
|---|---|---|---|
| **A. Утверждение не выполняется** | ранний `return` внутри теста, `if (!x) return`, цикл с литеральным индексом, ноль `expect` на прогоне, `describe` без `test` | GH-425 declared-contribution (`if (!declared) return` срабатывал всегда); gh403 `printed[1]` в цикле `i` | Тест доходит до конца, не проверив ничего или проверив не то |
| **B. Утверждение тавтологично** | `Array.isArray(x) === true`; обе стороны сравнения от одного производителя; копия сравнивается с копией; допуск шире любого расхождения (`toBeLessThanOrEqual(1)`); `> tol` при `tol === undefined` → `NaN > undefined` всегда `false` | calc-audit completeness; gh415 «document side» = тот же код; два пина GH-312 сверяли каждый свою копию; gh368 транскрипция движка; восьмой случай | Утверждение верно при любом коде |
| **C. Красный по соседней ветке** | защита A стоит после защиты B в том же пути; тест подаёт вход, который отбивает B, и приписывает результат A | `test_an_identity_field_cannot_be_emptied` — `''` → `null` → отбит проверкой на `null` раньше identity | Снять A — тест зелёный |
| **D. Сценарий не воспроизвёлся, отсутствие принято за отказ** | утверждение «ноль запросов / нет записи / нет оверлея» без утверждения, что путь вообще прошёл: страница отдала 500, задержка спрятала цепочку, скрипт не инициализировался | H2a/H2b при нуле запросов; пять сценариев при 500; S2 с задержкой 7 с; S5 на Reports, где мастер не инициализируется | Нечего было ловить, и тест это принял |
| **E. Структурный сторож с дырой в перечислении** | regex ловит одну форму записи из нескольких; сторожит 2 файла из 6; только негативные утверждения (убрал вызов целиком — зелёный); итерирует только то, что уже помечено | GH-440 `sends no PUT` — метод и адрес на разных строках; gh365 два `not`; GH-449 `forceFill`/присваивание; GH-453 сторож фикстур обходил только файлы со `scenario` | Пример пойман, класс — нет |
| **F. Обещание не совпадает с телом** | имя/комментарий описывают проверку, которой нет; патчится функция, удалённая из продукта; замер печатается как результат | GH-448 dry-run «reports the same thing» не сравнивал; gh401 «runs `_computeProgrammeDelivered`» тестировал `Array.reduce`; gh424 патчил удалённую `estimateMonthlySoilTemp`; gh410 сортировал по `undefined` | Читатель верит имени |
| **G. Данные: фикстура закрепила момент, не сценарий** | число в фикстуре — состояние базы в день съёмки; сравнение «фикстура против поверхности» проверяет неизменность базы, не продукт; выбор данных по числу из фикстуры | GH-452 (ткань), GH-453 (почва), GH-454 (селектор вызова по числу фикстуры), GH-456 | Тест зелёный, пока никто не трогал тестовый сайт, и красный от законной правки |

Общее у всех: тест **нельзя сделать красным снятием той защиты, ради которой он написан**. Это и есть определение
находки; всё остальное — способы её найти.

Не «просмотреть 2258 тестов». Три слоя: механические сигналы дают список кандидатов; ранжирование ставит опасное

## 2. Как доказывать по каждому

Правило одно: **находка и «не находка» обе доказываются прогоном, не рассуждением.** Строка реестра без вставленного
вывода jest/PHPUnit не принимается. Ниже протокол; исполнитель его не сокращает.

### 2.1. Протокол красной проверки (RC)

1. **Свойство.** В реестр: `P = <одно предложение>`, `код = <file:line>` защиты, `T = <файл :: имя теста>`.
2. **Копия.** `cp` защищаемого файла в `tmp/redcheck/<file>.orig`, `md5` в реестр. Git не используется (правило агентов);
   восстановление — только из этой копии.
3. **Мутация M.** Минимальная правка, которую дала бы настоящая регрессия P — не синтаксическая поломка: удалить строку
   гварда; инвертировать условие; вернуть из функции раньше; убрать один ключ из белого списка; сдвинуть число на
   величину больше допуска (GH-452: +0.4; GH-455: +0.5 г/м²). Файл после M обязан загружаться (`node -e "require(...)"`
   или прогон соседнего теста зелёный) — иначе красный будет от `SyntaxError`, а это класс C наоборот.
4. **Прогон T одного**: `npx jest <файл> -t '<имя>'` (PHPUnit: `php artisan test --filter`). Ожидание — **красный**.
5. **Причина.** В реестр вставляется строка падения. Принимается только если упавшее утверждение — то, что в п. 1(3)
   названо для P, и сообщение содержит наблюдаемое P (число, ключ, маршрут). Не принимается: `TypeError`,
   `Cannot read properties of undefined`, падение другого теста того же файла, таймаут, падение в `beforeAll`. Такой
   красный — не доказательство, а класс C или F; тест идёт в находки.
6. **Специфичность (обязательна для классов C и E).** Вторая мутация M′ — соседний гвард в том же пути (для C) или
   другая форма записи того же свойства (для E: `forceFill` вместо `update`, метод и URL на двух строках, второй файл
   из списка). Для C ожидание — T **зелёный** при M′ (T ловит своё, а не любое); для E ожидание — T **красный** при
   каждой форме. Красный от M′ у теста класса C означает, что T падает от чего угодно в этом пути, — записать, это
   не находка, но и не специфичный сторож.
7. **Восстановление.** `cp` из копии, `md5` совпал, T зелёный. В реестр — md5 до/после. Без совпадения md5 работа не
   принимается.
8. **Для live-тестов (D, G)** дополнительно: парный прогон на обычной загрузке без подмен (правило замеров, раздел 8
   плана GH-439), и мутация — на продуктовом пути (сдвиг значения в `assets/`), а не в тесте. Стенд один, прогоны
   ставятся в очередь через координатора; между собой не совмещаются.
9. **Для структурных сторожей (E)** мутация — в сторожимом исходнике: добавить нарушение в **каждой** форме из
   перечня форм (раздел 2.3) и в файле, который сторож считает покрытым; отдельно — уменьшить сторожимое множество
   (удалить одну фикстуру/один view из списка) и проверить, что сторож заметил уменьшение.

### 2.2. Что записывается (реестр, один файл на часть)

`files/fixes/26-08-17-hoxton-v6/Q26-ledger-part<N>.md`, по строке на тест:

```
| T | буквы 1.1 | P (предложение) | код | M (diff, 1–3 строки) | вывод красного (дословно, 1–3 строки) | M′ и результат | md5 до = после | вердикт: сторожит / находка-<буква> / нельзя сделать красным |
```

Строка с пустым «вывод красного» — не строка. Строка «сторожит» без M — не строка.

### 2.3. Перечень форм для структурных сторожей

Составляется один раз в части 0 и переиспользуется: для каждого сторожимого свойства — все способы записать нарушение в
этой кодовой базе. Начальный список из уже случившегося: `->update(['config'=>…])` / `forceFill()->save()` /
`$row->config = …; save()` / `updateOrCreate` / `DB::table()->update` (GH-449); `fetch(url, {method:'PUT'})` /
`apiFetch('PUT', …)` / метод и URL на разных строках / переменная с URL (GH-440); `localStorage.setItem(KEY)` /
`_ls.setItem` / ключ через переменную / namespaced-ключ (GH-439 стадия 3); фикстура без блока / с блоком без ключа /
исключение без причины (GH-453). Список живёт в реестре части 0 и пополняется каждой находкой класса E.

### 2.4. Быстрая мутация для тестов без сигналов

Сплошной слой. Для теста без сигналов 1.1 — одна мутация из п. 3 без специфичности п. 6, 5–10 минут на тест, тем же
протоколом записи. Не выполняется только для тестов, которые часть уже накрыла через RC соседа с тем же P (запись
«покрыт RC строки N»).

## 3. Что делать с найденным

Три исхода, признак выбора — ответ на вопрос «есть ли у свойства P нарушение, которое кто-то может внести»:

| Исход | Признак | Что именно |
|---|---|---|
| **Переписать** | P существует в продукте, нарушение возможно, и есть наблюдаемое, на которое можно утверждать | Утверждение переписывается на наблюдаемое P; RC повторяется по протоколу; в changelog — строка «shown failing by <M>» с выводом. Для класса C — добавить вход, который проходит соседний гвард; для E — одно утверждение на каждую форму из 2.3 и утверждение размера множества; для D — утверждение факта прохода (`assertPageRendered`, след расчёта, ответ 200) **до** утверждения отсутствия; для G — сравнение поверхность-с-поверхностью, состояние против заявленного сценария |
| **Удалить** | P больше нет (защита удалена из продукта вместе с тестом-патчем — gh424); тест дублирует другой, уже прошедший RC на то же P; тест — замер/печать без утверждения (probe) | Удаление с записью в реестр: какой тест теперь сторожит P, или «P не существует с GH-NNN» |
| **Оставить с пометкой** | Тест не сторожит, но документирует: пин формулировки, smoke «модуль грузится», `test.todo` | Имя переписывается на то, что тест реально гарантирует («loads without throwing», не «computes X»); в docblock — `// not a guard: <почему>`; в реестр — «оставлен как документация». Пометка обязательна, иначе через месяц он снова читается как сторож |

**Тест, который нельзя сделать красным.** Это не вердикт по чтению, а результат: три разные мутации по протоколу, все
зелёные, вывод вставлен. Дальше по порядку: (а) если P формулируется — переписать (исход 1) с новой RC; (б) если P
проверяемо только вживую — перенести в e2e с мутацией на продуктовом пути и парным обычным прогоном; (в) если P не
формулируется — удалить; (г) `test.todo` с текстом P допустим только когда P сформулировано, а поверхности для
утверждения ещё нет (например, ждёт эндпоинта) — с номером вопроса в `PLAN-remaining-defects-RU.md`. «Оставить как
есть, потому что зелёный» — не исход.

**Нельзя сделать красным по конструкции** — отдельный подкласс B: тавтологии. Их не чинят, их заменяют (GH-423:
`Array.isArray(bad)` → равенство именованному списку).

## 5. Как не завести восьмой случай

Два сторожа, заведённые 16.09, сами имели слепые зоны, и обе нашло ревью, не сторожа:

- gh447 «единственный писатель» ловил `->update([...])` и query builder, а не `forceFill()->save()` и присваивание
  свойства (GH-449). Его RC была честной — посаженный пример был пойман — и всё же не доказывала класс: пример был
  одной формы из четырёх.
- `fixtures-scenario-consistency` обходил только фикстуры, где `scenario` уже есть (GH-453): проверял правильность
  помеченного и не видел непомеченного. RC «фикстура объявляет deficient при 2.5 → красный» это не выявила.

Оба — класс E, и оба одного вида: **сторож проверяет элемент, а слепая зона — в перечислении.** Отсюда следует для
прохода и для каждого нового теста:

1. **RC доказывает пример; перечисление доказывается отдельно.** У каждого структурного сторожа в реестре два поля:
   «формы нарушения» (список 2.3, по одной посаженной на каждую) и «множество» (что итерирует, и независимая
   оценка его размера: `find … | wc -l` против длины списка в тесте, с утверждением равенства в самом тесте). Сторож
   без утверждения о размере множества — находка E, даже если все примеры пойманы.
2. **Мутацию выбирает не автор теста.** В части 6 и в ревью каждой новой правки ревьюер сам называет M по тексту P,
   не читая, что применил исполнитель; расхождение — повод переписать. Так поймались GH-449 и GH-453: ревьюер
   спросил «а если написать иначе», а не проверил, что посаженный пример ловится.
3. **Отрицательное утверждение всегда с положительным.** «Нет PUT» — рядом «есть PATCH с такими ключами»; «нет
   оверлея» — рядом «страница отрендерилась, скрипт инициализировался»; «ноль запросов» — рядом «цепочка дошла до
   точки, где запрос был бы». Тест из одних отрицаний не принимается в ревью (класс D/E).
4. **Класс A закрывается механикой, не дисциплиной**: `expect.hasAssertions()` глобально (часть 0; замер 16.09: восемь
   падений, все настоящие). Обхода изнутри теста у него нет — `expect.assertions(0)` не засчитывается, — и это правильно:
   честный probe выносится из `testMatch` (раздел 6, п. 2), а не помечается. Это единственный
   класс, который отсекается конфигурацией; остальные — только протоколом.
5. **Правило замеров** (раздел 8 плана GH-439) распространяется с live на все тесты: утверждение о числе, снятом под
   условием (стаб, задержка, чистый контекст, фикстурное число), идёт с названным условием в имени теста и в отчёте.
6. **Реестр — часть сдачи, не приложение.** Changelog-запись без строки «shown failing by <M>: <вывод>» для каждого
   нового или переписанного теста не принимается — это уже практика (9 записей с «shown failing» в changelog), план её
   делает обязательной.
7. **Проход сам себя не проверяет.** Часть 6 (10 % строк повторяет другой человек, своим выбором строк) — единственная
   защита от того, что исполнитель прохода записал «сторожит» по чтению. Без части 6 план не сдаётся.
8. **Сторож привязан к месту или к имени, а не к происхождению значения — отдельный приём, которого избегать** (добавлено
   17.09.2026, четыре случая за сутки: сторож GH-459, `gh461`, `gh365`, сторож стадии 1 GH-439). Тест проверял, где написано и
   как называется; гарантия была о том, откуда значение. Перенос чтения в хелпер строкой выше, переименование переменной,
   второе присваивание после верного — все проходят такой сторож по построению. Правило и два допустимых способа
   (сентинелы в источнике → ни один не достиг цели; AST-поток данных по всему файлу) — раздел 10.9 плана GH-439; regex по
   именам и телам функций — только дымовая проверка сверх них. В классификации раздела 0 это подкласс **E** (дыра в
   перечислении: перечислены места, а не источники); в мутациях RC (2.1, п. 6) для структурных сторожей добавляются мутации
   переноса — хелпер выше, другая функция, другое имя, второе присваивание.
9. **Текстовый сторож с ненайденным якорем обязан падать, не проверять пустоту** (добавлено 17.09.2026 по замеру:
   `gh299-aa-ceiling-consumers` — якорь со скобкой не находился, `slice(-1, …)` давал пустую строку, три `not.toMatch`
   проходили на ней; сторож умер молча при смене сигнатуры и упасть не мог). Класс A в чистом виде: утверждение выполняется,
   но над пустой строкой. Требование ко всем 31 файлу с якорями по исходнику: один хелпер `anchoredSlice(src, start, end)`
   в `tests/lib/`, бросающий при ненайденном якоре или пустом теле; сигнал в 1.1 — `indexOf('function …`/`.slice(` по
   исходнику без предшествующего `toBeGreaterThan(-1)`; смена сигнатуры функции — событие для всех сторожей с этим якорем,
   и хелпер делает его красным везде сразу.
10. **Множество, о котором сторож утверждает, задаётся тем, о чём гарантия, — четыре оси в заголовке каждого сторожа**
    (добавлено 17.09.2026 после четырёх случаев за день: подстрока вместо узла, снимок вместо обращения, одноэлементный
    стор, одиночная сборка вместо комбинированной). **Единица** (что есть один элемент: узел, путь, поле, метод), **момент**
    (когда наблюдается: на обращении, во время сборки), **различимость** (может ли утверждение отличить правильный элемент
    от чужого: два сайта, инверсия булевых, отравлено всё), **вход** (какой путь продукта порождает множество: тот, которым
    пользуется клиент; множество выводится из продукта, полнота утверждается отдельно от свойства), **носитель** (чем
    представлено то, о чём утверждение — строка, число, объект, функция, прокси, промис — и умеет ли проверка осматривать
    это представление; добавлено 17.09 после мёртвого обходчика сентинелов: искал строки, отравление отдавало
    функции-прокси). RC ревьюера — по мутации на каждую ось. Без пяти строк в заголовке сторож в ревью не принимается;
    у любой проверки отсутствия — позитивный контроль присутствия в том же файле. Подробно — план GH-439, 10.6,
    шестнадцатое и семнадцатое уточнения.
12. **Правило принятия живёт в артефакте и в инструменте, не в памяти** (добавлено 17.09.2026, двадцатое уточнение плана
    GH-439: принятое утром правило якорения на узел не перенеслось на сторож, написанный через несколько часов). Паспорт
    сторожа — обязательный блок в файле с полями: guarantee, claims (absence/effect), universe, пять осей,
    positive-control, exemptions (форма: file, function, узел по AST, what, why, until — никогда файл, счётчик или
    регулярка на несколько форм), ratchet, rc. Мета-сторож `tests/guard-passports.test.js` проверяет наличие паспорта и
    краснеет на известных анти-формах механически. В ревью — список строк по полям паспорта, который ревьюер заполняет;
    пустая строка не принимается. Часть 0 этого плана получает паспорт и мета-сторож как инструмент.
11. **Текстовый сторож доказывает только отсутствие над перечисленной вселенной; наличие эффекта доказывается
    наблюдением потребителя по значению или потоком данных** (добавлено 17.09.2026, восемнадцатое уточнение плана
    GH-439). В заголовке сторожа — какое из двух он утверждает; «наличие» без парного сторожа эффекта не принимается. В
    мутации RC (2.1, п. 6) добавляется «текст оставлен, эффект убран»: вызов с выброшенным результатом, присваивание в
    неиспользуемую переменную, ветка после `return`, тот же вызов с другим аргументом.

## 6. Открытые вопросы

1. Часть 2 требует стенда на 3.5 дня с перерывами; очередь и порядок с другими работами — координатор.
2. **Отвечено 16.09.2026 (после замера части 0).** Первая редакция предлагала для честных probe-тестов
   `expect.assertions(0)`; это не работает — `hasAssertions()` падает с тем же сообщением. Ответ: у probe-теста нет
   места в `tests/*.test.js`. Два исхода, по признаку «есть ли у замера инвариант»:
   - **Есть инвариант** (таблица должна иметь по строке на сайт, каждая с числом; отсортированность; равенство
     именованному списку) → это тест, утверждение пишется на инвариант, RC по протоколу. Так уже переписан
     `gh410-phosphorus-overshoot-probe` в GH-436 (сортировка по `undefined`).
   - **Инварианта нет, нужен только вывод** (замеры GH-424/426, аудиты, «напечатать и посмотреть») → файл переезжает в
     `tests/probes/<name>.probe.js`, вне `testMatch` (`**/tests/**/*.test.js` его не видит), запускается своим скриптом
     в `package.json` (`"probe:<name>": "node tests/probes/<name>.probe.js"` или `jest --testMatch` с явным путём) и не
     участвует в `npx jest`. Прогон probe по-прежнему обязателен там, где на его цифры опирается план, но он не
     сообщает «зелёный».
   Пометка через `expect.assertions(0)` или `expect(true).toBe(true)` запрещена: вторая — тавтология класса B, первая
   не работает. Замер части 0 показал, что среди восьми падений probe-тестов нет — все восемь настоящие сторожа с
   условным `expect`; переезд в `tests/probes/` нужен только тем файлам из 13 печатающих, у которых нет инварианта;
   список составляется в части 0 по каждому файлу отдельно.
3. Stryker в части 3 — пробовать или нет (+1 день, результат не заменяет протокол).
