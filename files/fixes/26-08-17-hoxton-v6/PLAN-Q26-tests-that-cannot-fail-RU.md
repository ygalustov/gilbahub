## 0. Обобщение: как тест перестаёт сторожить

Восемь случаев Вопроса 26 и девять из GH-436 сводятся к шести способам. Каждый способ даёт признак для механического
поиска (раздел 1) и свою мутацию для красной проверки (раздел 2). Классификация — рабочий инструмент прохода: у каждого
кандидата в реестре стоит буква.

| Буква | Способ | Случаи | Почему зелёный |
|---|---|---|---|
| **A. Утверждение не выполняется** | ранний `return` внутри теста, `if (!x) return`, цикл с литеральным индексом, ноль `expect` на прогоне, `describe` без `test` | GH-425 declared-contribution (`if (!declared) return` срабатывал всегда); gh403 `printed[1]` в цикле `i` | Тест доходит до конца, не проверив ничего или проверив не то |
| **B. Утверждение тавтологично** | `Array.isArray(x) === true`; обе стороны сравнения от одного производителя; копия сравнивается с копией; допуск шире любого расхождения (`toBeLessThanOrEqual(1)`); `> tol` при `tol === undefined` → `NaN > undefined` всегда `false` | calc-audit completeness; gh415 «document side» = тот же код; два пина GH-312 сверяли каждый свою копию; gh368 транскрипция движка; восьмой случай | Утверждение верно при любом коде |
| **C. Красный по соседней ветке** | защита A стоит после защиты B в том же пути; тест подаёт вход, который отбивает B, и приписывает результат A | `test_an_identity_field_cannot_be_emptied` — `''` → `null` → отбит проверкой на `null` раньше identity | Снять A — тест зелёный |
| **D. Сценарий не воспроизвёлся, отсутствие принято за отказ** | утверждение «ноль запросов / нет записи / нет оверлея» без утверждения, что путь вообще прошёл: страница отдала 500, задержка спрятала цепочку, скрипт не инициализировался | H2a/H2b при нуле запросов; пять сценариев при 500; S2 с задержкой 7 с; S5 на Reports, где мастер не инициализируется | Нечего было ловить, и тест это принял |
| **E. Структурный сторож с дырой в перечислении** | regex ловит одну форму записи из нескольких; сторожит 2 файла из 6; только негативные утверждения (убрал вызов целиком — зелёный); итерирует только то, что уже помечено | GH-440 `sends no PUT` — метод и адрес на разных строках; gh365 два `not`; GH-449 `forceFill`/присваивание; GH-453 сторож фикстур обходил только файлы со `scenario` | Пример пойман, класс — нет |
| **F. Обещание не совпадает с телом** | имя/комментарий описывают проверку, которой нет; патчится функция, удалённая из продукта; замер печатается как результат | GH-448 dry-run «reports the same thing» не сравнивал; gh401 «runs `_computeProgrammeDelivered`» тестировал `Array.reduce`; gh424 патчил удалённую `estimateMonthlySoilTemp`; gh410 сортировал по `undefined` | Читатель верит имени |
| **G. Данные: фикстура закрепила момент, не сценарий** | число в фикстуре — состояние базы в день съёмки; сравнение «фикстура против поверхности» проверяет неизменность базы, не продукт; выбор данных по числу из фикстуры | GH-452 (ткань), GH-453 (почва), GH-454 (селектор вызова по числу фикстуры), GH-456 | Тест зелёный, пока никто не трогал тестовый сайт, и красный от законной правки |

Общее у всех: тест **нельзя сделать красным снятием той защиты, ради которой он написан**. Это и есть определение
находки; всё остальное — способы её найти.

## 2. Как доказывать по каждому

Правило одно: **находка и «не находка» обе доказываются прогоном, не рассуждением.** Строка реестра без вставленного
вывода jest/PHPUnit не принимается. Ниже протокол; исполнитель его не сокращает.

### 2.1. Протокол красной проверки (RC)

1. **Свойство.** В реестр: `P = <одно предложение>`, `код = <file:line>` защиты, `T = <файл :: имя теста>`.
2. **Копия.** `cp` защищаемого файла в `tmp/redcheck/<file>.orig`, `md5` в реестр. Git не используется (правило агентов);
   восстановление — только из этой копии.
3. **Мутация M.** Минимальная правка, которую дала бы настоящая регрессия P — не синтаксическая поломка: удалить строку
   гварда; инвертировать условие; вернуть из функции раньше; убрать один ключ из белого списка; сдвинуть число на
   величину больше допуска (GH-452: +0.4; GH-455: +0.5 г/м²). Файл после M обязан загружаться (`node -e "require(...)"`
   или прогон соседнего теста зелёный) — иначе красный будет от `SyntaxError`, а это класс C наоборот.
4. **Прогон T одного**: `npx jest <файл> -t '<имя>'` (PHPUnit: `php artisan test --filter`). Ожидание — **красный**.
5. **Причина.** В реестр вставляется строка падения. Принимается только если упавшее утверждение — то, что в п. 1(3)
   названо для P, и сообщение содержит наблюдаемое P (число, ключ, маршрут). Не принимается: `TypeError`,
   `Cannot read properties of undefined`, падение другого теста того же файла, таймаут, падение в `beforeAll`. Такой
   красный — не доказательство, а класс C или F; тест идёт в находки.
6. **Специфичность (обязательна для классов C и E).** Вторая мутация M′ — соседний гвард в том же пути (для C) или
   другая форма записи того же свойства (для E: `forceFill` вместо `update`, метод и URL на двух строках, второй файл
   из списка). Для C ожидание — T **зелёный** при M′ (T ловит своё, а не любое); для E ожидание — T **красный** при
   каждой форме. Красный от M′ у теста класса C означает, что T падает от чего угодно в этом пути, — записать, это
   не находка, но и не специфичный сторож.
7. **Восстановление.** `cp` из копии, `md5` совпал, T зелёный. В реестр — md5 до/после. Без совпадения md5 работа не
   принимается.
8. **Для live-тестов (D, G)** дополнительно: парный прогон на обычной загрузке без подмен (правило замеров, раздел 8
   плана GH-439), и мутация — на продуктовом пути (сдвиг значения в `assets/`), а не в тесте. Стенд один, прогоны
   ставятся в очередь через координатора; между собой не совмещаются.
9. **Для структурных сторожей (E)** мутация — в сторожимом исходнике: добавить нарушение в **каждой** форме из
   перечня форм (раздел 2.3) и в файле, который сторож считает покрытым; отдельно — уменьшить сторожимое множество
   (удалить одну фикстуру/один view из списка) и проверить, что сторож заметил уменьшение.

### 2.2. Что записывается (реестр, один файл на часть)

`files/fixes/26-08-17-hoxton-v6/Q26-ledger-part<N>.md`, по строке на тест:

```
| T | буквы 1.1 | P (предложение) | код | M (diff, 1–3 строки) | вывод красного (дословно, 1–3 строки) | M′ и результат | md5 до = после | вердикт: сторожит / находка-<буква> / нельзя сделать красным |
```

Строка с пустым «вывод красного» — не строка. Строка «сторожит» без M — не строка.

### 2.3. Перечень форм для структурных сторожей

Составляется один раз в части 0 и переиспользуется: для каждого сторожимого свойства — все способы записать нарушение в
этой кодовой базе. Начальный список из уже случившегося: `->update(['config'=>…])` / `forceFill()->save()` /
`$row->config = …; save()` / `updateOrCreate` / `DB::table()->update` (GH-449); `fetch(url, {method:'PUT'})` /
`apiFetch('PUT', …)` / метод и URL на разных строках / переменная с URL (GH-440); `localStorage.setItem(KEY)` /
`_ls.setItem` / ключ через переменную / namespaced-ключ (GH-439 стадия 3); фикстура без блока / с блоком без ключа /
исключение без причины (GH-453). Список живёт в реестре части 0 и пополняется каждой находкой класса E.

### 2.4. Быстрая мутация для тестов без сигналов

Сплошной слой. Для теста без сигналов 1.1 — одна мутация из п. 3 без специфичности п. 6, 5–10 минут на тест, тем же
протоколом записи. Не выполняется только для тестов, которые часть уже накрыла через RC соседа с тем же P (запись
«покрыт RC строки N»).

## 3. Что делать с найденным

Три исхода, признак выбора — ответ на вопрос «есть ли у свойства P нарушение, которое кто-то может внести»:

| Исход | Признак | Что именно |
|---|---|---|
| **Переписать** | P существует в продукте, нарушение возможно, и есть наблюдаемое, на которое можно утверждать | Утверждение переписывается на наблюдаемое P; RC повторяется по протоколу; в changelog — строка «shown failing by <M>» с выводом. **Тест, который нельзя сделать красным.** Это не вердикт по чтению, а результат: три разные мутации по протоколу, все
зелёные, вывод вставлен. Дальше по порядку: (а) если P формулируется — переписать (исход 1) с новой RC; (б) если P

формулируется — удалить; (г) `test.todo` с текстом P допустим только когда P сформулировано, а поверхности для
утверждения ещё нет (например, ждёт эндпоинта) — с номером вопроса в `PLAN-remaining-defects-RU.md`. «Оставить как
есть, потому что зелёный» — не исход.

**Нельзя сделать красным по конструкции** — отдельный подкласс B: тавтологии. Их не чинят, их заменяют (GH-423:

## 5. Как не завести восьмой случай

Два сторожа, заведённые 16.09, сами имели слепые зоны, и обе нашло ревью, не сторожа:

- gh447 «единственный писатель» ловил `->update([...])` и query builder, а не `forceFill()->save()` и присваивание
  свойства (GH-449). Его RC была честной — посаженный пример был пойман — и всё же не доказывала класс: пример был
  одной формы из четырёх.
- `fixtures-scenario-consistency` обходил только фикстуры, где `scenario` уже есть (GH-453): проверял правильность
  помеченного и не видел непомеченного. RC «фикстура объявляет deficient при 2.5 → красный» это не выявила.

Оба — класс E, и оба одного вида: **сторож проверяет элемент, а слепая зона — в перечислении.** Отсюда следует для
прохода и для каждого нового теста:

1. **RC доказывает пример; перечисление доказывается отдельно.** У каждого структурного сторожа в реестре два поля:
   «формы нарушения» (список 2.3, по одной посаженной на каждую) и «множество» (что итерирует, и независимая
   оценка его размера: `find … | wc -l` против длины списка в тесте, с утверждением равенства в самом тесте). Сторож
   без утверждения о размере множества — находка E, даже если все примеры пойманы.
2. **Мутацию выбирает не автор теста.** В части 6 и в ревью каждой новой правки ревьюер сам называет M по тексту P,
   не читая, что применил исполнитель; расхождение — повод переписать. Так поймались GH-449 и GH-453: ревьюер
   спросил «а если написать иначе», а не проверил, что посаженный пример ловится.
3. **Отрицательное утверждение всегда с положительным.** «Нет PUT» — рядом «есть PATCH с такими ключами»; «нет
   оверлея» — рядом «страница отрендерилась, скрипт инициализировался»; «ноль запросов» — рядом «цепочка дошла до
   точки, где запрос был бы». Тест из одних отрицаний не принимается в ревью (класс D/E).
4. **Класс A закрывается механикой, не дисциплиной**: `expect.hasAssertions()` глобально (часть 0; замер 16.09: восемь
   падений, все настоящие). Обхода изнутри теста у него нет — `expect.assertions(0)` не засчитывается, — и это правильно:
   честный probe выносится из `testMatch` (раздел 6, п. 2), а не помечается. Это единственный
   класс, который отсекается конфигурацией; остальные — только протоколом.
5. **Правило замеров** (раздел 8 плана GH-439) распространяется с live на все тесты: утверждение о числе, снятом под
   условием (стаб, задержка, чистый контекст, фикстурное число), идёт с названным условием в имени теста и в отчёте.
6. **Реестр — часть сдачи, не приложение.** Changelog-запись без строки «shown failing by <M>: <вывод>» для каждого
   нового или переписанного теста не принимается — это уже практика (9 записей с «shown failing» в changelog), план её
   делает обязательной.
7. **Проход сам себя не проверяет.** Часть 6 (10 % строк повторяет другой человек, своим выбором строк) — единственная
   защита от того, что исполнитель прохода записал «сторожит» по чтению. Без части 6 план не сдаётся.
8. **Сторож привязан к месту или к имени, а не к происхождению значения — отдельный приём, которого избегать** (добавлено
   17.09.2026, четыре случая за сутки: сторож GH-459, `gh461`, `gh365`, сторож стадии 1 GH-439). Тест проверял, где написано и
   как называется; гарантия была о том, откуда значение. Перенос чтения в хелпер строкой выше, переименование переменной,
   второе присваивание после верного — все проходят такой сторож по построению. Правило и два допустимых способа
   (сентинелы в источнике → ни один не достиг цели; AST-поток данных по всему файлу) — раздел 10.9 плана GH-439; regex по
   именам и телам функций — только дымовая проверка сверх них. В классификации раздела 0 это подкласс **E** (дыра в
   перечислении: перечислены места, а не источники); в мутациях RC (2.1, п. 6) для структурных сторожей добавляются мутации
   переноса — хелпер выше, другая функция, другое имя, второе присваивание.
9. **Текстовый сторож с ненайденным якорем обязан падать, не проверять пустоту** (добавлено 17.09.2026 по замеру:
   `gh299-aa-ceiling-consumers` — якорь со скобкой не находился, `slice(-1, …)` давал пустую строку, три `not.toMatch`
   проходили на ней; сторож умер молча при смене сигнатуры и упасть не мог). Класс A в чистом виде: утверждение выполняется,
   но над пустой строкой. Требование ко всем 31 файлу с якорями по исходнику: один хелпер `anchoredSlice(src, start, end)`
   в `tests/lib/`, бросающий при ненайденном якоре или пустом теле; сигнал в 1.1 — `indexOf('function …`/`.slice(` по
   исходнику без предшествующего `toBeGreaterThan(-1)`; смена сигнатуры функции — событие для всех сторожей с этим якорем,
   и хелпер делает его красным везде сразу.
10. **Множество, о котором сторож утверждает, задаётся тем, о чём гарантия, — четыре оси в заголовке каждого сторожа**
    (добавлено 17.09.2026 после четырёх случаев за день: подстрока вместо узла, снимок вместо обращения, одноэлементный
    стор, одиночная сборка вместо комбинированной). **Единица** (что есть один элемент: узел, путь, поле, метод), **момент**
    (когда наблюдается: на обращении, во время сборки), **различимость** (может ли утверждение отличить правильный элемент
    от чужого: два сайта, инверсия булевых, отравлено всё), **вход** (какой путь продукта порождает множество: тот, которым
    пользуется клиент; множество выводится из продукта, полнота утверждается отдельно от свойства), **носитель** (чем
    представлено то, о чём утверждение — строка, число, объект, функция, прокси, промис — и умеет ли проверка осматривать
    это представление; добавлено 17.09 после мёртвого обходчика сентинелов: искал строки, отравление отдавало
    функции-прокси). RC ревьюера — по мутации на каждую ось. Без пяти строк в заголовке сторож в ревью не принимается;
    у любой проверки отсутствия — позитивный контроль присутствия в том же файле. Подробно — план GH-439, 10.6,
    шестнадцатое и семнадцатое уточнения.
12. **Правило принятия живёт в артефакте и в инструменте, не в памяти** (добавлено 17.09.2026, двадцатое уточнение плана
    GH-439: принятое утром правило якорения на узел не перенеслось на сторож, написанный через несколько часов). Паспорт
    сторожа — обязательный блок в файле с полями: guarantee, claims (absence/effect), universe, пять осей,
    positive-control, exemptions (форма: file, function, узел по AST, what, why, until — никогда файл, счётчик или
    регулярка на несколько форм), ratchet, rc. Мета-сторож `tests/guard-passports.test.js` проверяет наличие паспорта и
    краснеет на известных анти-формах механически. В ревью — список строк по полям паспорта, который ревьюер заполняет;
    пустая строка не принимается. Часть 0 этого плана получает паспорт и мета-сторож как инструмент.
11. **Текстовый сторож доказывает только отсутствие над перечисленной вселенной; наличие эффекта доказывается
    наблюдением потребителя по значению или потоком данных** (добавлено 17.09.2026, восемнадцатое уточнение плана
    GH-439). В заголовке сторожа — какое из двух он утверждает; «наличие» без парного сторожа эффекта не принимается. В
    мутации RC (2.1, п. 6) добавляется «текст оставлен, эффект убран»: вызов с выброшенным результатом, присваивание в
    неиспользуемую переменную, ветка после `return`, тот же вызов с другим аргументом.

## 6. Открытые вопросы

1. Часть 2 требует стенда на 3.5 дня с перерывами; очередь и порядок с другими работами — координатор.
2. **Отвечено 16.09.2026 (после замера части 0).** Первая редакция предлагала для честных probe-тестов
   `expect.assertions(0)`; это не работает — `hasAssertions()` падает с тем же сообщением. Ответ: у probe-теста нет
   места в `tests/*.test.js`. Два исхода, по признаку «есть ли у замера инвариант»:
   - **Есть инвариант** (таблица должна иметь по строке на сайт, каждая с числом; отсортированность; равенство
     именованному списку) → это тест, утверждение пишется на инвариант, RC по протоколу. Так уже переписан
     `gh410-phosphorus-overshoot-probe` в GH-436 (сортировка по `undefined`).
   - **Инварианта нет, нужен только вывод** (замеры GH-424/426, аудиты, «напечатать и посмотреть») → файл переезжает в
     `tests/probes/<name>.probe.js`, вне `testMatch` (`**/tests/**/*.test.js` его не видит), запускается своим скриптом
     в `package.json` (`"probe:<name>": "node tests/probes/<name>.probe.js"` или `jest --testMatch` с явным путём) и не
     участвует в `npx jest`. Прогон probe по-прежнему обязателен там, где на его цифры опирается план, но он не
     сообщает «зелёный».
   Пометка через `expect.assertions(0)` или `expect(true).toBe(true)` запрещена: вторая — тавтология класса B, первая
   не работает. Замер части 0 показал, что среди восьми падений probe-тестов нет — все восемь настоящие сторожа с
   условным `expect`; переезд в `tests/probes/` нужен только тем файлам из 13 печатающих, у которых нет инварианта;
   список составляется в части 0 по каждому файлу отдельно.

вообще имела смысл. **Свести к `normalized` — нельзя, и это надо сказать исполнителю вслух.**

**Поправка к формулировке 7.2:** верно не «формы без `normalized` не существует», а «продукт её не СТРОИТ;
попасть в склад она может только импортом связки на прогонщике». Для выбора дороги это ничего не меняет
(два случая всё равно закрепляли бы в фикстуре форму, которую продукт не производит), но меняет то, что
именно должно остаться единственным чтением.

### 7.3. Решение: вторая дорога ревьюера, и единственное чтение — объявленный читатель

**Первая дорога (два случая) отпадает по замеру:** пробы «только `normalized`» и «только `rawData`» в
продукте не встречаются, и два таких случая закрепили бы вымысел в фикстуре навсегда.

**Берётся вторая: недостижимые ветви из калитки уходят.** Остаётся одно чтение, и это **объявленный
читатель** — `GAIP_SampleManager.readingsOf('soil', active)` (экспортируется, `sample-manager.js:2614`), а не одно из
трёх полей. Причина та же, что в GH-591 и в пункте 3а: **собственный список имён рядом с объявленным —
это дефект, а не вариант написания.**

**Поведение при этом не меняется, и это проверено, а не предположено.** `normalizeValues`
(`sample-manager.js:1313-1368`) и `readingsOf` (`:1617-1656`) идут по ОДНОЙ карте (`SOIL_FIELD_MAP`) через ОДИН
разрешитель колонок (`_buildColumnIndex`) и отличаются только именем ключа. Пустота у них совпадает, **кроме
четырёх селекторов без имени показания** — `.gaip-soil-area-ha`, `.gaip-loi-0-2`, `.gaip-loi-2-4`, `.gaip-loi-4-6`
(`_readingKeyFor` отдаёт `CLASS_READING_KEYS[mapped] || null`, `:1579-1589`; сама карта — `:1573-1576`).
То есть проба, несущая **только** площадь или **только** послойный LOI, сегодня считалась бы «пришла»,
а после правки — нет. **Замер границы:** из 48 живых почвенных проб в базе **48 несут хотя бы одну
колонку с именем показания**, то есть случаев расхождения ноль
(`SELECT sample_type, COUNT(*), SUM(JSON_CONTAINS_PATH(payload,'one','$.pH','$.K','$.CEC','$.EC','$.OM', …))
FROM samples WHERE deleted_at IS NULL GROUP BY sample_type` — soil 48/48, water 8/8, tissue 4/4).
Граница названа вслух, а не спрятана.

### 7.4. Что после этого различает `gh578` — и чего он не различает никогда

не может его покрасить ни до правки, ни после. **Это не недостаток набора, а его граница, и её надо
написать в его же докблоке:** `gh578` стережёт КАЛИТКУ, а не читателя проб. Свидетелем читателя
служит живая оснастка (`tests/lib/sample-readings.js`), как в пункте 3а; два предмета смешивать не надо.

**Что набор различает после правки — третий случай, которого у него сейчас нет.** Сегодня есть два

нет** — калитка держит проход и ретраит, как при отсутствии пробы. Это не выдуманное положение: так
выглядит проба, чьи колонки карта не узнала, — ровно тот класс, который стоил измеренного pH в GH-591.
Именно этот случай и делает набор красным под мутацией «убрать проверку на пустоту».

## 8. СЛУЧАЙ, ИСТИННЫЙ ПРИ ЛЮБОМ ПОВЕДЕНИИ ПРОДЮСЕРА. Ноль в балансовых ионах (23.09.2026)

**Разбор, кода нет.** Класс — **B** из таблицы раздела 0: утверждение верно при любом коде.

### 8.1. Решение владельца и что из него исполнено

Её слова 23.09.2026: «если рассчитан лабораторией как ноль — надо писать ноль. А если нет его, значит
его не мерили».

| где | что с нулём | исполнено ли решение |
|---|---|---|
| `_ionsOf` (`hub-persistence.js:131-138`, GH-598) | числовой ноль сохраняется, отсутствующего ключа нет | **да** |
| `_traceIons` (`:2440-2445`, GH-599) — `NO3`, `PO4`, `Mn` | `!isNaN(v)`, ноль доезжает, отсутствие не даёт ключа | **да** |
| `ions` в записи (`:2553`) — восемь балансовых | `_meq` (`:2413`) даёт `(parseFloat(…) \|\| 0) / f`; ключ есть всегда, значение ноль в обоих случаях | **нет** |

**Решение исполнено там, где примера не приводили, и не исполнено на `CO3`, который и был примером.**
Находка ревьюера подтверждена по дереву.

### 8.2. Это не латентный случай — оба состояния есть в базе сегодня

Замер по восьми живым водным пробам (`samples`, `sample_type='water'`, `deleted_at IS NULL`):
**`CO3` измерен ровно нулём у шести** (пробы 54, 136, 137, 138, 139, 140) и **отсутствует у двух** (114, 115).
То есть оба состояния, которые владелец велела не схлопывать, сегодня стоят рядом в базе — и в записи
схлопываются в одно.

### 8.3. Почему случай зелён при любом поведении

`gh586-…test.js:317-331` утверждает две вещи о `water.ions`: ключ `CO3` есть (`:329`) и равен нулю (`:330`).
Блок `ions` записи собирается из восьми переменных `_meq` и потому **всегда несёт восемь ключей
с числовыми значениями**. Оба утверждения истинны и при починке, и при возвращённом дефекте — что
ревьюер и измерил: ноль падений при возвращённом фильтре.

### 8.4. Решение: обе дороги, но разными адресатами

**(1) Случай переставляется туда, где различие есть** — проба с `NO3: '0'`, утверждения о `water.traceIons`.
Там возврат фильтра `if (v > 0)` в `_ionsOf` уронит ключ и покрасит случай. Имя случая остаётся
верным, предмет — тот же; меняется ион, на котором он проверяется.

**(2) Для балансовых ионов различие в записи не выражено, и выразить его надо.** Довод — не вкус:
запись уже несёт **два канала для одного рода данных** — честный `traceIons` для трёх ионов и выведенный
`ions` для восьми, — и асимметрия задана не смыслом, а наличием коэффициента пересчёта.
**`ions` — это выведенный вид для арифметики (SAR, RSC, LSI), а не показания пробы.** Для арифметики
`\|\| 0` законен: отсутствующий ион и нулевой вкладывают одинаково. Дефект в том, что **выведенный вид
опубликован как единственный**, и измеренного состояния восьми ионов в записи нет нигде.

**Устройство, симметричное `traceIons` и выводимое, а не перечисляемое:** рядом с `traceIons`
ставится второй выведенный набор — то, что отдал объявленный читатель и для чего у баланса
коэффициент **есть**, в единицах самой пробы, с сохранённым нулём и без ключа для неизмеренного.
Два набора вместе дают ровно то, что проба измерила; `ions` остаётся как есть и остаётся выведенным.

### 8.5. Размер и куда это входит

**2 места, 2 случая, 0 миграций. Входит в уже идущую работу** (GH-598/599 — тот же блок, находка
его же приёмки), по правилу «найденное внутри работы чинится внутри работы».

| что | где, якорь | мест |

### 8.6. РЕШЕНИЕ ВЛАДЕЛЬЦА 23.09.2026 СНЯЛО РАЗВИЛКУ — устройство, размер, что видно клиенту

Её слова: «что за вопрос? делаем одинаково. 0 это ноль, нет измерений — пусто». Развилки для неё не

**УСТРОЙСТВО.** Рядом с `_traceIons` ставится второй выведенный набор — то, что отдал объявленный

`ions` (меквиваленты) остаётся как есть — это выведенный вид для арифметики, и `\|\| 0` в нём законен.

не трогаются** — они считают, а не печатают состав.

**ЧТО МЕНЯЕТСЯ В ТАБЛИЦЕ, ЧИСЛОМ И В ОБЕ СТОРОНЫ.** Замер по восьми живым водным пробам,

- **строк ПОЯВИТСЯ: 6** — строка карбоната со значением 0 на шести пробах двух площадок;
- **строк ИСЧЕЗНЕТ: 0.** Отсутствующий ион даёт меквивалент ноль и сегодня строки не даёт,
  так что у Russley (114 — семь отсутствуют, 115 — четыре) не меняется ничего.

**То есть изменение одностороннее: таблица приобретает строку для того, что действительно измерено,
и не теряет ни одной.** По главному правилу это в плюс: сегодня две площадки из трёх с водными
пробами не видят разницы между «карбонат померили, его нет» и «карбонат не мерили».

### 9.1. Предмет, проверен по дереву

### 9.2. Это тот же предмет, что 3т, и потому одно устройство

`k in rowSurface` — проверка **тождества ключа**, и она проваливается двумя способами сразу:
показание есть, а ячейки нет (3п), и показание есть, а строка зовёт его иначе — `Na` под именем
`soilNa`, `OM` вне поверхности (3т). **Оба сегодня молча падают в одну и ту же дыру** — «не моё дело», —
и потому чинятся одним решением, а не двумя.

### 9.3. Решение: вселенная судьи — ПРОБА, и исходов четыре, а не три

Ни первая дорога ревьюера в чистом виде (починить `dropped`), ни вторая (переименовать и завести
третий перечень) не закрывают 3т. **Берётся первая, доведённая до конца:** судья перебирает
**показания пробы** и каждому выносит один из четырёх исходов:

| исход | когда | сегодня |
|---|---|---|
| `agreed` | строка называет и совпадает на печатной точности | есть (`shared` минус остальные) |
| `disagreed` | строка называет, значения расходятся | есть |
| `blank` | ячейка есть, в ней `-` или пусто | сегодняшний `dropped`, под верным именем |
| `absent` | строка не называет нигде ни под каким объявленным именем | **нет, это и есть дыра** |

**Свойство, из-за которого выпасть больше нельзя, и оно утверждаемое:** четыре исхода в сумме
равны числу показаний пробы. Это одна строка утверждения и она закрывает класс: новый способ
потерять показание красит судью сам.

**Имена (3т) входят сюда же и НЕ гадаются.** Судья получает карту имён явным входом:
показание ищется на поверхности под объявленным именем (`Na → soilNa`), и показание без записи
в карте попадает в `absent` — **видимо, а не молча**. То есть карта не список-исключение, а способ
назвать соответствие; её неполнота не прячется, а печатается исходом.

**Положительный контроль остаётся первым:** `agreed.length > 0`. Пустое пересечение согласуется
с любым утверждением.

### 9.4. По оси расхождения чинить нечего — и это ДОКАЗЫВАЕТСЯ, а не только измеряется

Ревьюер прогнал 200 000 пар и получил ноль случаев «новый говорит расхождение, старый согласие».
Это не случайность выборки: старый предикат соглашается только при точном числовом равенстве,
новый — при равенстве на печатной точности, то есть соглашается строго чаще; нечитаемое значение
оба зовут расхождением. **Множество расхождений нового — подмножество старого по построению**,
и обратный случай невозможен, а не просто не встретился. Вывод «7 из 7» по этой оси стоит;
меняется только отбор.

### 9.5. Размер числом

**3 места, +2 случая, +1 утверждение полноты, 0 миграций.** У судьи два читателя, оба названы.

### 9.6. Где живёт соответствие имён: в продюсере, и судья его ИЗМЕРЯЕТ, а не хранит (24.09.2026, ночь)

Раздел 9.3 решил, что судья получает карту имён явным входом, и не сказал, где эта карта живёт. Повод — ложное `absent`
у `Na` на `Burns` после починки отбора (судья от пробы, GH-617). Всё ниже снято чтением дерева и базы; прогонов не было.
**Номера строк не даю, только якоря: дерево сейчас правится.**

**Что измерено.** Переименований на поверхности почвы два рода, и они разные по существу:
- **то же показание под другим именем.** Проба несёт `Na`, строка зовёт его `soilNa` (`hub-persistence.js`, якорь
  `soilNa:       (_si.ppm && _si.ppm.Na)`). На `Burns` значения равны: проба 53 — `Na` 0.2, строка 68 — `soilNa` 0.2;
- **производное.** Проба несёт `EC` (`sample-manager.js`, `CLASS_READING_KEYS`, `'.gaip-soil-ec': 'EC'`), строка несёт
  `ECe` = EC1:5 × множитель текстуры от 5 до 10 (`hub-tissue-v3.js`, якорь `ECe: (function() {`). Сравнивать их на
  равенство нельзя: это разные величины.
- Числа по базе (точное совпадение ключа, то есть нижняя граница — резолвер колонок терпит регистр и суффиксы):
  `Na` или `Na_ppm` несут **44** почвенные пробы из 48, EC под одним из ключей карты — **41** из 48.
- **Предсказание, прочитано, не исполнено:** починенный судья на каждой площадке, чья проба несёт EC, назовёт `EC`
  потерянным. Это второе ложное срабатывание того же рода, и его ещё никто не видел. На `Burns` его нет: у пробы 53
  колонки EC нет.

**Способы, и почему выбран последний.**
1. **Карта в судье, записанная рукой** (`{Na: 'soilNa'}`). Закрывает случай, и её устаревание громкое: новое имя даст
   `absent`, а не тишину. Но производное она выразить не может, а очевидная запись `EC → ECe` неверна: даст ложное
   `disagreed` с разницей в 5–10 раз.
2. **Переименовать поле строки в `Na`.** Меняет хранимую форму: 67 строк несут `soilNa`, миграций нет, у поля два
   читателя, и один из них печатает человеку (`water-balance-analysis.js`, «Soil Na: … ppm»). Отклонено.
3. **Объявить соответствие в `analysis-result.schema.json`.** Место одно, но само имя поля остаётся в продюсере
   (двух его дверях) и в `SampleAnalysisController`. Это два написания со сторожем — то самое «дублирование с ремнём»,
   от которого владелец просила уходить.
4. **Измерить.** Соответствие — свойство поведения продюсера. Судья берёт настоящую пробу фикстурой, меняет одно
   показание на δ, прогоняет цепочку «проба → строка» на офлайновом стенде (`tests/lib/orchestrator-bench.js` грузит все
   скрипты `/hub`, включая `hub-tissue-v3.js` и `hub-persistence.js`) и смотрит, какое поле поверхности сдвинулось:
   ровно на δ — то же показание под этим именем; иначе — производное; ни одно — показание строкой не несётся.

**Решение: 4. Соответствие живёт в продюсере и больше нигде.** Судья его измеряет перед каждым суждением и не хранит.
Довод: имя написано в одном месте, поэтому расходиться нечему. Производное выражается исходом, а не записью. Поле,
которое появится завтра, — например `OM` после 3у, под любым именем, — найдётся без чьей-либо памяти.

**Исходов у судьи становится пять:** к `agreed`, `disagreed`, `blank`, `absent` (9.3) добавляется **`derived`**. Для
производного проверяется только **присутствие**: показание измерено, значит производное поле не пустое. Равенство не
проверяется. Утверждение полноты из 9.3 остаётся: сумма пяти исходов равна числу показаний пробы.

**Закрывает ли класс — прямо.** Подкласс «поле строки ↔ показание пробы» закрывается целиком, для всех показаний сразу:
`Na`, `EC`, `OM` и будущие. **Весь ночной класс — нет.** Общее у трёх ночных случаев одно: две системы имён соединены
совпадением написания, и промах молча даёт запасной ответ. Но соединения стоят в разных местах, и лекарство у них разное:
- `loi_0_20` против `LOI_0_2` — колонка лаборатории против карты;
- `sand_profile` против `sand-profile` — значение конфига против ключа таблицы, это 3ф: промах должен давать отказ,
  а не `default`;
- `Na` против `soilNa` — поверхность строки против показаний пробы, это здесь.

Сквозной приём «промах соединения громкий» — предложение, в эту работу не входит и требует решения.

**Граница, названа.** Не установлено, доходит ли стенд до сборки состояния почвы внутри обработчика кнопки
(`hub-tissue-v3.js`, там же, где якорь `ECe: (function() {`, читает текстуру из формы). Поэтому первый шаг разработчика —
положительный контроль: `pH` измеряется как то же показание под тем же именем. Не измерилось — судья красный с надписью
«стенд не дошёл до продюсера», запасной карты у него нет.

**Размер: ≈ 4 места, +3 случая, +1 положительный контроль, 0 миграций. Клиент ничего не видит — это тест.**

| что | где, якорь | мест |
|---|---|---|
| измерение соответствия + исход `derived` | `tests/lib/row-vs-sample.js`, `function judge` | 1 |
| прогон «проба → строка» с одной сдвинутой величиной | адаптер к `tests/lib/orchestrator-bench.js` | 1 |
| случаи: переименованное поле найдено измерением; производное → `derived`, не `disagreed`; не несётся → `absent` | `tests/gh609-…test.js` | 1 |
| живой судья берёт измеренное соответствие | `tests/e2e/gh591-restore-a-row-live.test.js`, якорь `judgeRowAgainstSample(rowSurface` | 1 |

Дешёвый вариант (1) — 1 место и 1 случай, но `EC` тогда остаётся ложным красным или становится ложным `disagreed`.

**Найдено попутно, в эту работу не входит.**
- **Второй продюсер той же поверхности, со своим списком псевдонимов** — `SampleAnalysisController::run` (маршрут
  `/api/samples/{id}/analyse`, его зовёт выбор пробы на `/analysis`). CEC он ищет только как `CEC` и `cec`.
  **4 почвенные пробы на 2 площадках** несут CEC только как `CEC_meq100g`: прогон его находит, сервер — нет.
  Это тот же ночной класс в четвёртом месте. Что это видно на экране при выборе такой пробы, прочитано по коду,
  не проверено на странице. **Починка меняет то, что печатается человеку, — решение владельца.**
- **`Na_ppm: 0` в состоянии почвы** (`hub-tissue-v3.js`, якорь `Na_ppm: 0,`). Ноль изготавливается при отсутствии.
  Замещается, только когда проба несёт натрий (якорь `o.soil.Na_ppm = safeNum`). Иначе ноль уходит в
  `assessSoilSodium(e.soil.Na_ppm` и в сборщик с `Na_ppm: e.soil.ppm?.Na || 0`. Тот же класс, что 3р и 3л.
  Достижимость не мерена: натрий не несут 4 пробы из 48.

### 9.7. Карта имён: строится один раз на прогон и от ПРОБЫ, а не от состояния (24.09.2026, ночь)

**Вход:** вопрос ревьюера о цене — один полный офлайновый прогон `/hub` на показание — и его вторая находка: судья
меряет три показания, и три — это чей-то выбор, а не исчерпанность. Сверено с деревом:
`tests/lib/producer-name-map.js` (GH-626) и `tests/gh626-the-producer-says-what-it-calls-a-reading.test.js`.

**Что измерено чтением — исполнение ушло от 9.6 в двух местах, и оба важнее цены.**
1. **Сдвигается не показание пробы, а поле готового состояния.** `surfaceFor(soil)` кладёт `soil` прямо в
   `state.inputs`. Какое поле состояния несёт какое показание, решают функции в тесте (`withNa` пишет и `Na_ppm`, и
   `ppm.Na`; `withPh` — `pH_water`). То есть первое звено, «показание пробы → поле состояния», — то самое, где имена и
   расходятся, — **написано рукой в тесте**. Это вторая карта имён, та, от которой 9.6 уходил.
2. **Случай `EC` — тавтология.** `withEc = (s, v) => ({… EC1_5: v, ECe: v * 7 })`: тест сам кладёт производное
   `ECe = v × 7`, а затем утверждает, что `ECe` производное с множителем от 5 до 10. Продукт вычисляет `ECe` в
   обработчике кнопки (`hub-tissue-v3.js`, якорь `ECe: (function() {`, множитель по текстуре). Стенд этот обработчик не
   исполняет. **Прочитано, не исполнено:** если убрать вычисление `ECe` из продукта, случай останется зелёным. Класс B
   раздела 0: обе стороны от одного производителя. Мутацию выбирает ревьюер, и я её только называю.
3. **«Три» — выбор.** Сторож меряет `pH`, `Na`, `K`, `EC`, выбранные рукой. Остальные показания пробы — `P`, `Ca`, `Mg`,
   `S`, `Fe`, `Mn`, `Zn`, `Cu`, `B`, `CEC`, `OM` — не меряются. Судьба третьего имени того же рода решена чтением (4.13а),
   а не этим сторожем.

**Решение.**
- **Вселенная показаний — объявленная, не выбранная:** `readingKeysFor('soil')` из `sample-manager.js`, 15 имён.
  Меряются все, и новое показание в карте лабораторных имён попадает в замер без чьей-либо памяти.
- **Сдвигается показание в строке лаборатории** (`values` пробы), и цепочка идёт целиком: `readingsOf` → чтение пробы
  прогоном → сборка состояния почвы → продюсер. Функций `withX` в тесте нет.
- **Препятствие, названо: середина цепочки не вызывается.** Сборка состояния почвы, вместе с вычислением `ECe`, стоит
  внутри обработчика кнопки прогонщика и читает форму. Чтобы стенд прошёл цепочку, эта сборка выносится в функцию,
  которую зовут и обработчик, и стенд. Это перенос кода без изменения поведения, **1 место в продукте**, и первое
  условие всего решения. Без него карта не может быть измерена от пробы. Честный запасной путь только один: сказать
  это вслух, а не вернуть `withX`.
- **Строится один раз на процесс, не на показание и не на нажатие.** Первым делом прогон строит всю карту:
  1 базовый прогон и 15 сдвинутых, каждый на свежей загрузке стенда, чтобы глобалы одного прогона не протекли в
  другой. Дальше карта живёт в памяти процесса. Живая проба строит её сама, перед нажатием, тем же вызовом.
- **Где живёт: нигде, кроме памяти процесса.** Файла карты в дереве нет. Если замер цены покажет, что 16 загрузок
  стенда на каждую живую пробу дороги, допустим кэш **вне дерева**, в каталоге временных файлов. Ключ кэша — отпечаток

**Звено «момент» — устройство есть, механическое.**

- утверждение, полученное чтением, едет с пометкой «прочитано, не исполнено» и в очередь как дефект не принимается,

|---|---|---|
| момент, прогон | отпечаток печатает сам прогон | **да** |
| момент, база | отметка в том же запросе | форма; её отсутствие видно получателю |

### 11.1. Что входит в отпечаток — чтобы он различал состояния, а не просто присутствовал

**Два разных механизма, у каждого свой вопрос.**

1. **Личность дерева** — «то же ли дерево у меня и у тебя». sha-256 по отсортированным строкам
   `относительный путь \0 sha-256 содержимого \n`. Время изменения сюда **не входит**. Одинаковое содержимое на двух машинах
   или после `touch` даёт один отпечаток. Переименование, удаление и новый файл меняют отпечаток. Печатаются первые 12
   знаков.
2. **Движение внутри прогона** — «трогал ли кто-то дерево, пока я шёл». Сравнивается не хэш, а **`ctime`
   каждого файла** с моментом старта, плюс перечень путей в начале и в конце.

**Почему не хэш в начале и в конце, как в наброске.** Ревьюер мутирует файл и возвращает его. Если это пришлось на
середину чужого прогона, хэши начала и конца равны, а часть наборов прочитала мутанта. По `ctime` такой случай виден.
`mtime` тоже не годится: возврат копией `cp -p` ставит прежний `mtime`, а `ctime` вручную не выставляется.

**Вселенная — всё дерево `gilbahub/` минус объявленные исключения, а не перечень папок.** Новая папка попадает во
вселенную сама. Ошибка в эту сторону — лишний недействительный прогон, а не пропущенная правка.
- **Исключения**, у каждого своя причина:
  - `node_modules/`, `app/vendor/`, `app/node_modules/` — зависимости; их представляет `package-lock.json` и
    `app/composer.lock`, которые во вселенной остаются;
  - `app/storage/`, `app/bootstrap/cache/` — стек пишет туда сам во время живых прогонов: логи, скомпилированные шаблоны;
  - `docs/`, `memory/` — тесты их не читают, а `docs/instructions.md` правится вместе с каждым фиксом (Change log);
  - `files/` — координатор пишет туда живой документ всё время. С `files/` во вселенной недействительным был бы
    каждый прогон;
  - `coverage/`, `.phpunit.result.cache`, `.phpunit.cache` — пишет сам прогон;
  - `.DS_Store` в любом месте — Finder пишет его когда угодно.
- **Два файла из `files/` входят поимённо**, потому что их читают тесты: каталог `files/samples/templates`
  (`gh402-no-silent-multisite-turf.test.js`) и `files/fixes/26-08-17-hoxton-v6/dev-db-snapshot-2026-09-10.sql`
  (`gh410-phosphorus-lever-measurement.test.js`). Найдено `grep -rhoE "['\"/](tools|data|templates|docs|files)/…" tests`:
  больше ни одного.
- **Стоимость, замер 24.09:** ≈ 870 файлов, ≈ 22 МБ, `shasum` по всем — **0,14 с**. Кэшировать нечего.

**Вселенная одна на Jest и на PHPUnit.** Один модуль и одна таблица исключений. Прогон Jest и прогон PHPUnit на одном
дереве печатают **один и тот же** отпечаток.

### 11.2. Кто пишет и кто читает

**Один модуль — `tests/lib/tree-fingerprint.js`.** В нём таблица исключений и две функции: «отпечаток и перечень
с `ctime`» и «что сдвинулось с момента T». Больше таблицу исключений не держит никто.

**Пишут — только прогоны, сами:**
- **Jest:** `globalSetup` — печать `[tree] <hash12> start · <root> · <n> files · newest change: <path>, <N> s before
  start`, состояние кладётся в `globalThis`. `globalTeardown` — сверка. `globalSetup` и `globalTeardown` идут в одном
  родительском процессе, и `globalThis` между ними общий — так это описано у Jest. Подключается строками в
  `jest.config.js` рядом с GH-457. Это значит, что и `npx jest <один файл>`, и `npm run test:e2e*` печатают отпечаток
  без чьей-либо памяти.
- **PHPUnit:** контейнер `gilba_app` видит только `app/` и `assets/`. Поэтому отпечаток снимается **на хосте**
  обёрткой `npm run test:php -- <аргументы>`: печать `start`, затем `docker exec gilba_app php artisan test <аргументы>`,
  затем сверка. Одна реализация и одна вселенная с Jest.
  - **Обход закрыт:** `bootstrap` в `app/phpunit.xml` меняется с `vendor/autoload.php` на
    `tests/bootstrap.php`. Он подключает автозагрузку и отказывается работать, если нет переменной, которую передаёт
    обёртка (`docker exec -e`). Текст отказа называет команду обёртки.
  - Сегодня PHPUnit запускают как `docker exec gilba_app php artisan test --filter=GhNNN`, и после работы так будет
    нельзя. Это изменение порядка работы команды, не продукта. Решение моё.
- **Печать без прогона — `npm run tree`.** Тот же модуль, только строка отпечатка. Её и читает получатель.

**Читают:**
1. **Сам прогон, в конце** — механически, см. 11.3.
2. **Получатель числа, по приёму воспроизведения.** Отчёт о прогоне едет со строками `[tree] … start` и
   `[tree] … end`. Отчёт без строки `end` неполон. Получатель сверяет отпечаток отчёта со своим (`npm run tree` или строкой
   своего прогона). Равны — расхождение результатов настоящее: нестабильный тест, окружение, база. Не равны — числа
   несравнимы, спорить не о чем, правда его — для его дерева.
3. **Ревьюер, для доказательства возврата после мутации.** Контрольный прогон до мутации и прогон после возврата
   печатают отпечатки, и они обязаны быть равны. Равенство доказывает, что возвращено всё и точно. Сегодня это доказывают
   копией и `md5`, а они в его режиме не проходят — Вопрос 94. **Не проверено**, проходит ли в его режиме
   `npm run tree`. Прогон Jest у него проходит — на этом держится вся его приёмка. Если проходит — Вопрос 94 теряет
   предмет в части возврата. Это наблюдение для координатора, в работу не входит.

### 11.3. Что происходит, когда прогон и отпечаток расходятся — главное

**В конце прогона модуль собирает сдвинувшееся:**
- файлы вселенной с `ctime` ≥ момента старта;
- пути, которые появились или исчезли.

Из этого вычитаются записи самого прогона (ниже).
- **Пусто** → `[tree] <hash12> end · unchanged during run`. Прогон действителен, код выхода прежний.
- **Не пусто** → `[tree] TREE MOVED DURING RUN — results void`, а под ним **перечень сдвинувшегося поимённо**, с
  временем каждого. Не число: число не различает, что сдвинулось, и чьё. **Код выхода ненулевой, какой бы ни была
  сводка.**

**Где стоит эта строка — это и есть устройство.** Прочитано в `@jest/core`: сводка `Tests: N passed` печатается
репортёрами внутри `scheduleTests`. Потом идёт `globalTeardown`, потом `processResults`, который выставляет код выхода.
Отсюда:
- сверка живёт в `globalTeardown`, и строка о недействительности печатается **последней**, под сводкой. Агент, который
  смотрит хвост вывода, видит её первой;
- при сдвиге `globalTeardown` **бросает** ошибку с этим текстом. По чтению `runGlobalHook` ошибку пробрасывает, и
  `processResults` не выполняется. **Не проверено**, что процесс Jest 30 выходит при этом ненулём. Это первый замер
  разработчика, и он показывается выводом `echo $?`. Если выходит нулём — код выхода ставится явно
  (`process.exitCode`), и это тоже показывается.

**Записи самого прогона.** Два режима записи пишут в `tests/fixtures` во время прогона:
- `store-shapes-live.test.js` при `GILBA_RECORD`;
- `gh428-outer-soil-temp-live.test.js` при `GILBA_GH428_RECORD`.

Без вычета они объявляли бы себя недействительными. Модуль даёт `declareOwnWrite(path)`: тест, перед тем как писать,
кладёт путь в файл прогона, адрес которого `globalSetup` передаёт в `process.env`. Сверка вычитает эти пути и
печатает их отдельной строкой `[tree] written by this run: …`. **Не проверено**, доходит ли переменная, выставленная в
`globalSetup`, до рабочих процессов Jest. Замер — прогон записи в конце не должен быть недействительным. Остальные записи
тестов по умолчанию уходят во временный каталог или выключены, пока не задана переменная. Прочитано у всех мест,
которые нашёл `grep writeFileSync|appendFileSync|screenshot(` по `tests`. Переменная, указывающая в дерево, — выбор
запускающего; такой прогон объявит себя недействительным, и это верно.

### 11.4. Закрывает ли отпечаток тот же класс, что правило «число воспроизводит не автор»

**Нет. Он закрывает одно звено из трёх, и в этом звене — механически.** Считаю по шести случаям раздела 10:

| случай | звено | отпечаток | правило воспроизведения |
|---|---|---|---|
| 3 «четыре красных набора», прогон посреди правки | момент, прогон | **ловит сам**, прогон объявляет себя недействительным без получателя | не нужно для этой части |
| прогон **между** двумя правками — дерево цельное, но промежуточное | момент, прогон | не ловит: сдвига нет. Даёт два факта: отпечаток, по которому получатель видит «не моё дерево», и `newest change … s before start` — порога нет, суждение у читателя | нужно |
| 4 «68 строк», стенд подрос | момент, база | не касается | нужно; форма — `COUNT(*)`, `MAX(id)` |
| 2, 5, 6 «34 файла», «99 мест», «7 мест» | признак, число посчитано человеком | не касается: это не прогон | нужно |
| 1 — 3ф, чтение двух концов без пути | путь | не касается | нужно |

**Итог:**
- **Отпечаток заменяет правило ровно в одном месте:** «момент» для прогона тестов. В этом месте правило сегодня
  требует отметку, которую нечем снять, — отпечатка в дереве нет. После работы строку заполняет прогон, а не память
  автора.
- **Остальное остаётся за правилом**, и причина одна: у числа, посчитанного человеком, у утверждения по чтению и у
  числа из базы нет прогона, который напечатал бы свой момент. Второе исполнение другими руками — единственный
  механизм, который там есть.
- **Отпечаток усиливает правило для прогонов.** Сегодня два прогона, давшие разное, — это спор. С отпечатком
  равные отпечатки означают настоящее расхождение, разные — несравнимость. Спорить не о чем в обоих случаях.

### 11.5. План

1. **Замер первым — и он же положительный контроль.** Во временном каталоге — не в дереве — вселенная из трёх
   файлов, `jest --config` на неё, корень передаётся переменной `GILBA_TREE_ROOT`. Корень печатается в строке
   `start`: инструмент печатает, что видел. Показать выводом:
   (а) без изменений — `unchanged`, код 0;
   (б) файл изменён во время прогона — `void`, файл назван, код ≠ 0, `echo $?`;
   (в) изменён и возвращён копией `cp -p` — `void`;
   (г) запись через `declareOwnWrite` — действителен, путь в `written by this run`.
   Контрольный (а) печатается **до** утверждений (GH-650).
2. `tests/lib/tree-fingerprint.js` — модуль и таблица исключений (1).
3. `globalSetup` и `globalTeardown` — два маленьких файла в `tests/lib` (2), подключение в `jest.config.js` (1).
4. `declareOwnWrite` в двух режимах записи (2).
5. `package.json`: `tree` и `test:php` (1). `app/phpunit.xml` → `tests/bootstrap.php` с отказом без переменной
   обёртки (2).
6. Проверка на живом дереве: один `npx jest` по короткому набору, вывод целиком — строки `start` и `end` вокруг
   сводки. Один `npm run test:php -- --filter=Gh654` — те же строки. Один прямой `docker exec … php artisan test` —
   отказ с текстом.

**Размер: ≈ 9 мест, 5 случаев** (а–г и отказ PHPUnit). **0 миграций, 0 продуктовых файлов.** Набросок говорил
«3 места, 1 тест». Выросло из-за трёх вещей, которых набросок не видел: вселенная одна на два прогонщика, записи самого
прогона и обход PHPUnit.

### 11.6. Подводные камни

- **Сверять только `ctime`, личность — только содержимым.** Если перепутать — `touch` будет делать деревья
  «разными», а возврат через `cp -p` станет невидимым.
- **Не превращать исключения в перечень включений.** Новая папка пропадёт из вселенной молча.
- **Нельзя проверять устройство правкой настоящего файла дерева из теста:** это сделает недействительным сам
  проверяющий прогон и чужие прогоны. Только временная вселенная через `GILBA_TREE_ROOT` (п. 1).
- **Строка `void` не должна уходить в середину вывода.** Если Jest, получив ошибку `globalTeardown`, печатает что-то
  после неё — показать, что последним остаётся текст о недействительности.
- **Отпечаток не заменяет контрольный прогон и не подтверждает зелёное.** Он говорит только, на каком дереве получено
  число. Порядок приёмки — контрольный зелёный, мутация ревьюера — не меняется.
- **Код — без кириллицы и без ссылок на вопросы.** Только `GH-NNN` этой работы.

### 11.7. Границы — что остаётся открытым

- **Прогон между правками** не ловится автоматически. Остаются отпечаток и строка о последнем изменении перед стартом.
  Суждение за получателем.
- **База во вселенную не входит.** Недействительность по базе невозможна по построению: живые наборы сами пишут в
  базу, и их начало и конец расходятся всегда. Момент базы — форма правила (`COUNT(*)`, `MAX(id)`), не автомат.
- **Кэш конфигурации Laravel** (`artisan config:cache`, `route:cache`) и opcache меняют поведение стека без правки
  дерева. `app/bootstrap/cache` исключён сознательно: туда пишет стек. Сегодня кэши у нас не включаются. Если
  включатся, живой прогон может идти не на том коде, который описывает отпечаток.
- **Новый тест, читающий из `files/`**, во вселенную не попадёт. Пересчитывается той же командой `grep`, что в 11.1;
  сегодня таких два.
- **Число, посчитанное человеком, утверждение по чтению, число из базы** — за правилом воспроизведения (11.4).

**Открытых вопросов к владельцу нет.**
