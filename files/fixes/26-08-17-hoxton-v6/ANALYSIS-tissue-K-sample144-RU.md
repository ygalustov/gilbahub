## 1. Что именно изменилось 12.09 и была ли это намеренная правка

**Лог `gilba_web`, 12.09.2026 (UTC), один браузер, один сеанс:**

```
08:18:45 GET /plan → GET /api/samples?…tissue → PUT …/config/gaip          (Generate)
08:18:46 GET /analysis → GET /data
08:18:59 GET /plan → PUT …/config/gaip ×4                                   (Generate)
08:24:28 GET /analysis → POST /api/sites/sync, POST /api/samples/sync
08:24:39 GET /plan → PUT …/config/gaip ×4                                   (Generate)
08:26:31 GET /analysis → 08:26:32 GET /data → 08:26:33 GET /data/tissue
08:26:54 PATCH /api/samples/144   referer http://127.0.0.1:8080/data/tissue   ← правка K → 1.05
08:26:54 GET /data/tissue
08:27:06 GET /plan                                                            (следующий Generate; savedAt конфига 08:27 в срезе GH-439)
```

User-Agent всех строк: `Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) … Chrome/152.0.0.0 Safari/537.36` — настольный Chrome.
Харнессы Playwright ходят как `HeadlessChrome`: таких строк в логе 315 257, и **ни одна** из них не обращалась к
`/api/samples/141` или `/api/samples/144`. База: `samples.id = 144`, `updated_at = 2026-09-12 08:26:54`, `modified_by_user_id = 1`
(`yuryg@…`, `is_admin = 1` — общий логин, которым пользуются и люди, и e2e). Строка `site_summaries.id = 67` (`source_sample_id = 144`)
пересчитана в ту же секунду — обычный путь `SampleController::update()`.

Это правка руками через форму Data > Tissue, между двумя нажатиями Generate на Plan. Кто именно из людей сидел за этим Chrome —
по данным не установить (общий логин); что это не тест и не агент — установлено по User-Agent и по отсутствию обращений
харнесса к пробе. Намеренность: человек открыл именно тканевую пробу и поменял именно K; случайной эту правку считать не на
чем. Что он хотел получить — в данных нет.

**Та же картина у правки 08.09 (на 2):** `08.09 22:38:23 GET /data → 22:38:30 PATCH /api/samples/141` (почва K 40 / P 40) →
`22:40:25 GET /data/tissue → 22:40:32 PATCH /api/samples/144` (ткань K → 2) → `22:40:34 GET /plan` → PUT ×4. Тот же настольный
Chrome/152, тот же логин. Changelog GH-380 фиксирует это как «tissue K 2 %, as edited through the UI on 2026-09-09» без
объяснения, зачем 2. Фикстура `e2e-parity-test5-soccer.json` записана по этому состоянию (`_source`: «read 2026-09-09»; в брифе
«фикстура от 10.09» — расхождение на день, по содержимому `_source` дата чтения 09.09).

**Создание пробы:** `26.08.2026 08:48:23 POST /api/samples`, referer `/data/tissue`, тот же настольный Chrome — ручной ввод
через форму, не импорт. Значение K = 1.05 стоит с момента создания: тест `tests/gh361-tissue-gate-k-p-ratio.test.js:1-15`
(GH-361, конец августа) читает его из базы и сам отмечает: «the audit's own Hoxton tissue K reads 3.05%, evidently a different
capture of a similar site, but N and P match exactly».

**Итог по хронологии K пробы 144:** 26.08 создана с 1.05 (руками) → 08.09 22:40 UTC поставлено 2 (руками, при подготовке
GH-380) → 12.09 08:26 UTC возвращено 1.05 (руками). Изменения между 08.09 и 12.09 у пробы нет: `updated_at` одно.

## 2. Какое число верно агрономически

**Проба 144 — копия отчёта Хокстона.** Handover `GAIP_Hub_Defect_Handover_Hoxton_v6_2026-08-16.md:985`:
«Tissue: N 4.57, P 0.62, K 3.05, Ca 0.27, Mg 0.21, S 0.47 %; Fe 588, Mn 189, Zn 87, Cu 24.2 ppm».
Payload пробы 144 сегодня: `{"K":"1.05","N":"4.57","P":"0.62","S":"0.47","Ca":"0.27","Cu":"24.2","Fe":"588","Mg":"0.21","Mn":"189","Zn":"87"}`.
Девять из десяти элементов совпадают до знака, отличается только K, и отличается одной цифрой: 3.05 → 1.05. Это не «другая
съёмка похожего сайта», как предположил GH-361: у другой съёмки не совпали бы девять чисел из десяти. Это тот же отчёт с
одной неверно введённой цифрой (или сознательно изменённой — по данным не различить; см. раздел 6).

**Что это значит по диапазону.** Канонический диапазон K для райграса в коде — `tissue-engine.js:71` и
`soil-nutrition-analysis.js:1256`: `K: { lo: 2.00, hi: 3.42 }` (Spencer, набор для perennial ryegrass; тот же диапазон
печатает экспорт, `word-export.js:9081`, и приводит handover `:433-443`). Критический порог для K — `range.lo * 0.8 = 1.6`
(`word-export.js:3046`).

| K, % | Статус по диапазону 2.00–3.42 | Что делает продукт |
|---|---|---|
| 3.05 (отчёт клиента) | в норме | тканевый gate GH-361: K/N = 3.05/4.57 = 0.667 против табличного 100/180 = 0.556 (`nutrition-requirement-core.js:167`) — вынос K **выше** табличного на 20 %. Это направление и описано в аудите D07a («модель занижает вынос K») |
| 2 (правка 08.09) | ровно на нижней границе: `low = false`, `critical = false` | K/N = 0.438 — вынос K **ниже** табличного на 21 % |
| 1.05 (26.08 и с 12.09) | ниже критического порога 1.6 | K/N = 0.230 — вынос K ниже табличного на 59 %; в экспорте печатается «Tissue K critically low (1.05%) … apply foliar potassium immediately» (`word-export.js:4811`) |

Вывод: должно печататься то, что дал лабораторный отчёт, — **3.05**. Ни 1.05, ни 2 лабораторными значениями не являются. 1.05 у
райграса с N 4.57 % — тяжёлый дефицит, несовместимый с остальным вектором в норме; 2 — граница диапазона, выбранная рукой.
Отдельно: с 1.05 dev-стенд три недели прогонял тканевый gate D07a в направлении, обратном находке аудита (gate занижал K
вместо повышения), и это никем не было замечено, потому что число «настоящее» и в тестах, и в базе.

## 3. Если верно 1.05 — почему фикстура записывала 2

Не применимо: 1.05 не верно (раздел 2). Для полноты: фикстура записывала 2, потому что 08.09 K был поставлен на 2 руками при
подготовке GH-380, и фикстура честно сняла состояние базы на 09.09. На момент создания она была верна как снимок базы и
неверна как агрономическое ожидание — как и 1.05 до неё.

## 4. Если верно 2 — где отклонился расчёт

Не применимо: расчёт не отклонялся. Обе поверхности печатают то, что в базе, и согласны между собой; падает только сравнение
входа с фикстурой. Ни один расчётный тест харнесса не красный.

## 7. Поправка владельца (16.09.2026) — проверка фактом

Утверждение: «снижение было намеренным: тестировали сценарий нехватки калия и снизили оба показателя, почвенный и тканевый,
до 1.05». Проверено по логу `gilba_web` (все записи в пробу 141 за всё время) и по базе.

**1. Снижался ли вместе с тканевым почвенный K.** Все записи в пробу 141: 24.08 ×3, 26.08, 06.09, **08.09 22:38:30 UTC** —
последняя. 12.09 в пробу 141 не писал никто: ни `PATCH`, ни `POST /api/samples/sync` (два sync 12.09 в 08:24 и 08:26 прошли,
но `samples.updated_at` у 141 остался 08.09, значит payload не менялся). Значение почвенного K сегодня — **40 ppm**
(порог S277 — 78.2, то есть ниже порога); 07.09 фикстура `test5-soccer-sample141.json` читала 276. Значения 1.05 у почвы не
было никогда: 1.05 — доля процента, единица ткани; в почве K в ppm.

**2. Совпадает ли дата с 12.09.** Нет. Обе пробы одним сеансом правились **08.09** (22:38 почва 276 → 40, 22:40 ткань 1.05 →
**2**, то есть ткань тогда **подняли**). 12.09 правилась только ткань (2 → 1.05), почва не трогалась.

**Что подтверждается и что нет.** Намерение «сценарий нехватки калия по почве» подтверждается данными: почва ниже порога с
08.09, и фикстура GH-380 сама строится на этом (`_whyThisSample`: ниже порога S277). Формулировка «снизили оба до 1.05 12.09»
данным не соответствует по трём пунктам: почва снижена до 40, не до 1.05; сделано 08.09, не 12.09; ткань 08.09 была не
снижена, а поднята до 2, и снижена обратно до 1.05 только 12.09. При этом 1.05 у ткани — значение с момента создания пробы
26.08, так что «сценарий с тканевым K 1.05» существовал с 26.08 по 08.09 и снова с 12.09; окно с K 2 (08.09–12.09) — это
состояние, которое сняла фикстура.

**Отменяет или уточняет.** Уточняет. Раздел 2 остаётся верным как факт: 3.05 — значение отчёта клиента, 1.05 — ниже
критического порога. Меняется статус числа 1.05: не «одна неверная цифра при копировании», а заявленное владельцем намерение.
Если владелец подтверждает это, п. 1 раздела 5 (править пробу 144 на 3.05) снимается, п. 3 (docblock gh361/gh368: 1.05 —
не отчёт клиента, а сценарий) и п. 6 остаются, а вопрос сводится к двум решениям: что должна ждать фикстура и где жить
сценарию. Без подтверждения разбор остаётся в редакции разделов 2 и 5.

**Почему фикстура ждёт 2.** Потому что 08.09 при подготовке GH-380 ткань подняли до 2 и фикстуру сняли с этого состояния
09.09. Причина подъёма не записана. Возможное объяснение, не проверенное: при K 2 `low` и `critical` ложны, и в экспорте нет
строки «Tissue K critically low» — парити-харнессу, который сверяет структуру документа, это проще. Это догадка; в
changelog GH-380 и в фикстуре обоснования нет.

**Где место сценарию нехватки калия — на этой пробе или на отдельной.** Решение владельца; довод такой.

- Парити-харнесс по своему назначению (`_purpose` фикстуры) пинит входы и по построению падает на любой их правке: «If
  someone edits these samples again, update currentInputs here». Проба, которую правят руками под сценарии, и проба,
  которую харнесс держит как эталон входов, — это два разных назначения, и на одном объекте они спорят при каждой правке;
  именно это и произошло дважды (08.09 и 12.09).
- Вторая тканевая проба на **том же** сайте сценарий не решает: Plan и экспорт берут хронологически последнюю тканевую
  пробу в зоне (GH-372); проба с более поздней датой молча подменит 144 на обеих поверхностях, с более ранней — не будет
  прочитана вовсе, в другой зоне — не спарится с почвенной 141 (зона `Other`).
- Отдельный сайт («Test5 - NZ — K scenario» или подобный) с собственной почвенной (K 40) и тканевой (K 1.05) пробами: сценарий
  правится сколько угодно, харнесс на Test5 его не видит. Цена — один сайт через мастер и две пробы через формы. Тогда
  Test5 / 144 возвращается к роли замороженного набора Хокстона (K 3.05), которого handover прямо просил («Freeze the Hoxton
  dataset as a test fixture», assertion 7 — вектор вердиктов по ткани), и у которого сегодня в dev-базе нет дома.
- Оставить сценарий на 144 (K 1.05) и обновить фикстуру на 1.05 с пометкой `_scenario` — самый дешёвый путь, и по данным он
  соответствует состоянию базы бо́льшую часть времени с 26.08. Цена: набор Хокстона с K 3.05 нигде не лежит как живые
  данные (направление gate D07a проверяет один юнит-кейс в `gh361`, живой поверхности с 3.05 нет), и следующая ручная
  правка сценария снова уронит харнесс.
  Заметить стоит, что почвенный K 40 уже сценарное значение (у клиента 199), и фикстура его принимает — так что «Test5 —

**Как закрепить, чтобы фикстура несла название сценария.**

Предложение (форма на выбор владельца; ниже — одна конкретная):

- В каждой фикстуре, где есть тканевые или почвенные входы, блок `scenario`, например:
  ```json
  "scenario": {
    "soilK":   { "state": "deficient", "rule": "below floor of the resolved certificate range", "value": 40 },
    "tissueK": { "state": "deficient", "band": { "lo": 2.0, "hi": 3.42, "criticalBelow": 1.6 }, "value": 1.05,
                 "why": "owner's K-deficiency scenario, set by hand; NOT the client's reading (Hoxton 3.05)" }
  }
  ```
  Допустимые `state`: `deficient` (ниже `lo`), `normal` (между `lo` и `hi`), `sufficient` (не ниже `lo`, синоним для
  случаев «достаточно»), `irrelevant` (число на утверждение не влияет; хранится для replay). Для `irrelevant` значение
  всё равно записывается — с этим словом рядом.
- Один общий jest `tests/fixtures-scenario-consistency.test.js`: загружает каждую фикстуру с блоком `scenario` и проверяет,
  что `value` соответствует `state` относительно `band` (для почвы — относительно `rule`, если порог известен фикстуре).
  Записать «что было в тот день» без слова состояния станет невозможно: без `state` тест падает; с `state`, которому
  число не соответствует, — тоже падает. Расхождение видно при `npx jest`, а не через три недели.
- В e2e-предусловии F1 — не «фикстура равна базе», а «база соответствует заявленному состоянию» (для `deficient`: значение
  в базе ниже `criticalBelow` или ниже `lo`, по выбору владельца), и в отчёте прогона печатать «tissue K 1.05 в базе,
  заявлено deficient, порог 1.6». Правка числа в базе под другой сценарий тогда ломает предусловие с понятной строкой
  «база в состоянии normal, фикстура заявляет deficient», а правка внутри сценария (1.05 → 1.2) не ломает ничего.
- В docblock тестов с зашитыми числами — та же строка одним предложением: `// tissue K 1.05: deficiency scenario (below
  critical 1.6), not the client's reading` / `// tissue K: value irrelevant to this assertion`.
- На самой пробе — по желанию владельца — сценарий в ярлыке (`_label: "Soccer — K deficiency scenario"`), чтобы на странице
  Data было видно, что это не данные клиента. База остаётся источником истины, ярлык — только подпись.
