## 2. Устройство

1. **Клиент шлёт только изменённые поля.** Форма запоминает значения, **пришедшие с сервера при загрузке**, и в
   `patch`/`clear` уходят только отличающиеся. Нетронутое поле не едет вовсе.
2. **К каждому изменённому полю — условие:** `expected: {"turf.construction": "sand_profile", …}` — значение, которое
   человек видел. Для `clear` так же.
3. **Сравнивает только сервер, внутри того же `SiteConfigWriter::mutate`, под той же блокировкой.** Если текущее
   значение поля не равно `expected`, ответ `409` с текущими значениями расходящихся полей. Что писать при
   расхождении — всё или ничего, — решает владелец, ссылка в п. 4. До её решения — ничего: это единственный вариант,
   который не оставляет состояния, которого не хотел никто.
4. **`expected` не хранится и данными не становится.** Сервер только сравнивает. По форме это значения страницы на
   пути к серверу, поэтому сказано вслух: правило «браузер не хранит ничего, что потом записывается» соблюдено —
   записывается изменение, а не показанное.
5. **Решает один — сервер.** Своих слияний клиент не делает. Он получает готовый ответ: записано, или вот поля,
   изменившиеся с тех пор, как вы открыли страницу. Образец — `analysis-result.schema.json`: решает сервер, страница
   показывает.
6. **Условие обязательно.** Изменение без `expected` — `422`. Иначе новый писатель без условия тихо вернёт нынешнее
   поведение.
7. **Программа питания (№6, №7) — вторая часть.** Штамп координат и есть условие, только на одно поле. Обобщение:
   программа несёт значения входов, на которых посчитана, и сервер сравнивает их с текущими. Входы берутся из
   перечня входов и графа (`PLAN-calculation-inputs-RU.md` 4.6), а не списком здесь. Поэтому вторая часть — после
   стадии 0б той работы.
8. **Писатели на `/hub` (№8–10).** `/hub` — не клиентская поверхность. По правилу проекта контрол, который
   перестал работать, потому что убран путь записи, убирается, а не чинится. Поэтому эти писатели либо получают
   условие, если им нужно остаться, либо уходят вместе с контролом. Выбор по каждому делает разработчик и называет
   его в сдаче.

## 2а. Вторая гонка — строка площадки, у которой замка нет (находка ревьюера 24.09, проверена по дереву)

**Вход:** находка ревьюера о записи координат из бандла (`site-data-transfer.js`, якорь
`var _loc = bundle.siteConfig.location;`, сегодня `:299-313`) в `PATCH /sites/{id}`. Его суждение о законности этой
записи — вопрос владельцу, ссылка в п. 4. Здесь только устройство.

**Что измерено чтением.**
- **У координат объявлен владелец — строка площадки.** `FieldOwners::OWNERS` (`app/app/Support/FieldOwners.php`):
  `location.name → location_name`, `location.lat → latitude`, `location.lon → longitude`, `timezone → timezone`.
  Значения в конфиге — выводимые копии.
- **Путей, которые пишут строку площадки, два, и замок у них разный.**
  - `SiteController::update` (`PATCH /sites/{id}`): `$site->update($data)` — **без транзакции и без блокировки**.
    Потом `deriveOwnedCopies` пишет копии в конфиг через `SiteConfigWriter::mutate`, под замком конфига. Но значения
    для копий он берёт `$site->refresh()` **до того**, как замок взят (якорь `private function ownedColumnValues`).
  - `patchConfig`: владеемые поля из патча уходят в колонки через `$site->update($context['siteSync'])`, и это
    **изнутри** замка строки конфига.
- **Писателей строки площадки на клиенте три:** Settings Site (`apiFetch('PATCH', '/sites/' + siteId, payload)`),
  Settings Turf (`soil_texture_override`) и импорт бандла на `/hub` (`site-data-transfer.js`). Последний берёт цель из
  глобала страницы (`GAIP_HUB_CONFIG.activeSiteId`), а значения — из привезённого файла.

**Что гонится.**
1. **Два `PATCH /sites/{id}` в одни колонки** — Settings Site в двух вкладках, Settings против импорта. Строка:
   последний побеждает, молча. Это та же потеря, что в п. 1, на другом маршруте.
2. **Копия расходится с владельцем.** A пишет строку и читает её; B пишет строку, читает, пишет копии; A пишет копии
   из своего устаревшего чтения. В строке значение B, в `config.location` — A. Тот, кто читает конфиг, видит не то,
   что лежит у владельца.
3. **`update` против `patchConfig`** — оба пишут строку площадки, один снаружи замка конфига, другой изнутри.

**Ответ на вопрос «закрывает ли приём обе гонки»: в нынешнем виде нет, только ту, что через `config/gaip`.**
Расширение, чтобы закрыть обе:
- **Условие на поле — и на `PATCH /sites/{id}`, для владеемых колонок.** `expected` по тем же правилам п. 2: сравнивает
  сервер, при расхождении `409`, без условия `422`. Какие колонки владеемые, говорит `FieldOwners::OWNERS`, второй
  список не заводится.
- **Одна дверь для владельца и его копии.** Запись строки площадки и вывод копий идут в **одной** транзакции.
  Значения для копий берутся **внутри** неё, а не `refresh()` снаружи. Это исполнение того же приёма GH-447: замок
  перестаёт быть правилом, которое каждый вызывающий помнит, и становится единственным путём.
- **Порядок замков — один на всех путях: сначала строка `sites`, потом строка `site_configs`.** Сегодня `patchConfig`
  берёт конфиг и изнутри пишет площадку, а `update` пишет площадку и потом берёт конфиг. Если оба возьмут
  настоящие замки в сегодняшнем порядке, это взаимная блокировка. Поэтому `patchConfig` при владеемых полях сначала
  блокирует строку площадки.

**Размер сверх п. 3: ≈ 4 места, 2 теста.** `update` — условие и транзакция (1); `patchConfig` — порядок замков (1);
одна дверь для строки площадки с копиями (1); Settings Site — `expected` на владеемые поля (1). Тесты: копия не
расходится с владельцем при двух чередующихся записях; `update` без условия на владеемое поле — `422`. Импорт бандла
на `/hub` в размер не входит: по правилу проекта контрол на `/hub` убирается, а законность самой записи — вопрос
владельцу (п. 4).

**Не установлено:** воспроизводится ли расхождение копии на живом стеке. Прочитано, не исполнено, поэтому в стадию 1
добавляется второй замер.

## 5. Подводные камни

- **Сравнение — только внутри `mutate`.** Вынесенное из-под блокировки, оно вернёт гонку между проверкой и записью.
- **«Показанное» — это пришедшее с сервера, а не поле после автозаполнения формы.** Иначе дефолт формы (`generic`)
  станет ожидаемым и даст ложный конфликт или ложное «ничего не изменилось».
- **Сторож `gh447` утверждает «писатель один»:** всё идёт через тот же `mutate`, второго писателя не появляется.
- **`savedAt` внутри `traffic.schedule`** (якорь `savedAt: new Date().toISOString()`) — данные секции, а не условие.
  Путать нельзя.
- **Приёмка без красного замера стадии 1 не принимается.** Зелёный тест конфликта без показанной сегодняшней потери
  ничего не доказывает.

## 6. Границы — что остаётся незакрытым и почему

- **Какую гонку закрывает приём — прямо.** Условие на поле из п. 2 само по себе закрывает **только первую** гонку —
  через `config/gaip`, под замком `SiteConfigWriter::mutate`. **Вторую — строку площадки через `PATCH /sites/{id}` —
  закрывает только расширение п. 2а:** условие на владеемые колонки, одна транзакция для строки и копий, единый
  порядок замков. Если п. 2а отложить, вторая гонка остаётся открытой, и это граница, а не умолчание.
- **Импорт бандла на `/hub`** пишет координаты из привезённого файла в площадку, выбранную глобалом страницы. Эта
  работа его не чинит. По правилу проекта контрол на `/hub` убирается. Законность такой записи — вопрос владельцу
  (п. 4). Пока ни одно не сделано, этот путь пишет строку площадки без условия.
- **Колонки строки площадки вне `FieldOwners`** — `name`, `site_type`, `soil_texture_override`, `attributes_json` и
  другие — гонятся так же, но копий в конфиге у них нет. Условие на них в работу не входит: предмет пункта 17 —
  конфиг и его владельцы. Остаток по числу: в валидации `update` 10 полей, из них 4 владеемых (`location_name`,
  `latitude`, `longitude`, `timezone`), без условия остаются 6.
- **Одно поле у двух людей с одинаковым `expected`:** первый записан, второй получает конфликт. Разрешает человек, не
  автомат.
- **Вложенные объекты** (`turf.siteHistory`, `turf.led`, `traffic.schedule`) сравниваются по пути объекта. Разные
  подполя одного объекта из двух мест дадут конфликт, а не слияние. Это лишний конфликт, зато не потеря.
- **`gssh` (стадион)** пишется целиком через `updateConfig`. Свой план, решение 7, не трогается.
- **Программа вне штампа координат** остаётся устаревшей до второй части.
- **Сколько раз это уже теряло данные у клиента, по базе не измерить:** `updated_at`/`savedAt` не говорят, чьё значение
  затёрто.
