## 2. Что устроено неправильно

1. **У зоны нет личности.** Место опознаётся текстом подписи через `derive()`; список зон площадки — имена без
   идентификатора; переименование рвёт историю, опечатка рождает вторую зону.
2. **Тип — догадка, а не выбор.** Четыре места угадывают его по буквам имени; в базе он лежит как слово в пробе, а не у
   зоны; три словаря расходятся; сервер переводит ключ в отображаемое имя по своей таблице из восьми.
3. **Отсутствие типа неотличимо от «прочее».** Подстановка при загрузке (`sample-persistence.js:687`) стирает разницу для
   всех потребителей; ещё 19 мест повторяют её.
4. **Категория дублирует зону в каждой пробе** (`zone`/`_zone` при `_label`) и живёт отдельно от списка зон.
5. **Журналы носят четвёртый словарь** с молчаливым `'greens'`.

Пункты 1–2 — один дефект: нет объекта «зона» с владельцем на сервере; 3–5 — следствия.

## 3. Устройство

- **`zone_types`** — таблица (`id, key, label, sort_order`), засеяна словарём **поверхностей**: 11 ключей
  (`green fairway tee rough approach collar bunker sports_pitch goal_area centre other`) + `cotula_bowling_green` = **12**;
  водные ключи (`bore recycled potable surface`) в него **не входят** — это словарь вида источника воды, поле воды (ниже); страницы получают её с сервера (`GAIP_HUB_CONFIG.zoneTypes`), клиентские таблицы
  `ZONE_LABELS`/`AREA_GUIDANCE`/`FALLBACK_*` строятся по `id`, не по слову. Подсказки по площади (`AREA_GUIDANCE`) — поле
  у типа или таблица по `zone_type_id`.
- **`zones`** — таблица (`id, site_id, name, zone_type_id NULL, sort_order, timestamps, soft delete, unique(site_id,
  lower(name))`). Колонки `type_source` нет: перенесённые зоны типа не несут (4.3), а у заведённой человеком тип выбран
  им — различать нечего.
- **`samples.zone_id`** — FK, NULL допустим; `payload._label` остаётся именем визита («Green 1 (June 2025)»), `payload.zone`
  и `_zone` больше не пишутся.
- **Владелец на сервере** — `ZoneService`: `resolveOrCreate(site, name)` (решение владельца: нет — завести, без типа),
  `rename`, `setType`, `list`; права на входе как в разделе 11 плана по 31 (`canEditSite`); `SampleController` три пути
  записи вызывают `resolveOrCreate` вместо `mergeZoneNameIntoSite`/`applyZoneMeta`.
- **Settings → Zones — первичный путь.** Обычная работа при настройке площадки: человек заводит зону и выбирает тип
  (селект пустой до выбора, значения из `zone_types`); переименование; у зоны без типа — пометка «Type not set».
  Заведение из импорта (имя без типа) и перенос — вторичные пути, оба оставляют тип пустым, чтобы его выбрали здесь.
- **Data**: селект имени зоны из `zones` (есть, `:2236`) с созданием; селект категории `dat-f-zone` и список `ZONES` уходят;
  CSV — имя → `resolveOrCreate`.
- **Импорт** (пять путей 1.3): имя → `resolveOrCreate`; детекторы (четыре) уходят; отсутствующее имя — проба без зоны
  (`zone_id NULL`, GH-549), генерация `Sample_…`/`Unknown` как **имени** остаётся идентификатором визита, но в зону не
  превращается.
- **Потребители типа**: тип по `zone.zone_type_id`; нет типа — **исход** «Type not set» как своя группа/подпись, не
  «other»; 20 мест 1.4 → одна функция `zoneTypeLabel(zone)` в общем модуле (`zone-key.js` уже общий).
- **Личность вместо текста у читателей**: шесть вызывателей `derive()` получают `zone_id`; ключи графиков

## 4. Переход — чтобы у клиента ничего не рассыпалось

1. **Сев `zone_types`** — 16 строк.
2. **Зоны из двух источников на площадку:** `attributes_json.zones` ∪ различные `_label` проб **только** `sample_type IN
   ('soil','tissue','loi')` — тот же фильтр, что у сервера сегодня (`:144, :325, :439`); на стенде второе ⊂ первого —
   проверено, у клиента проверяется тем же запросом до миграции. Слияния нет: одна зона на каждое различное имя без
   учёта регистра. **Водные пробы в перенос зон не входят** (решение владельца 22.09): их `_label` остаётся именем
   пробы, `zone_id` — NULL, а `_zone` (`bore/surface`) переносится в `water_source_type_id`; пустой `_zone` (Russley, две
   пробы) — NULL, без подстановки. Команда переноса печатает отдельно: **зон создано** (по площадкам и всего),
   **из них с хотя бы одной пробой**, почвенных/тканевых привязано, водных пропущено, водных с видом источника и без.
   **Что она напечатает на стенде (база 22.09, замер до команды):** зон **70** на десяти площадках — это сумма списков
   (Test1 16, Burns 15, New test 11, Federal Golf 10, test4 8, Test5 4, Russley 3, по одной у трёх; Canberra и Test6 —
   ноль), потому что подписи проб входят в списки целиком; из них **с пробами 35** — пары «площадка + подпись» (Burns 15,
   New test 11, Russley 3, по одной у шести); различных подписей во всей базе **23** — это число команда не печатает,
   оно о тексте, а не о зонах (замеры Ники подтверждены: 23, 35, 9 площадок с пробами). Привязано 52, водных пропущено 8
   (6 с видом источника, 2 без). **Ручной работы владельцу — тип у 70 зон**, не у 35: 35 зон Test1, Federal Golf и test4
   заведены в списках без проб и тоже стоят без типа. Проба воды с именем места («9th») в зоны
   **не попадает** — фильтр по типу пробы, не по имени; если зона «9th» когда-нибудь заведена вручную, водная проба к
   ней не привязывается по построению.
3. **Тип зоны при переносе — пустой у всех.** Решение владельца 22.09: «можете пустым оставить, и я потом руками
   проставлю». Основание, записанное рядом: угаданный тип с пометкой выглядит заполненным полем, и до него могут не
   дойти руки; пустое поле само просится, чтобы его заполнили; ни одна цифра от пустого типа не меняется — тип в
   расчёты не входит (1.1, измерено). `_zone` проб при переносе не читается вовсе. **Видимое изменение после
   миграции:** переключатель проб показывает все зоны в одной группе «Type not set», пока владелец не проставит типы в
   Settings; графики, отчёты и Plan не меняются (они по месту, не по типу). Объём ручной работы — 4.2, число зон.
4. **`samples.zone_id`** — по `(site_id, lower(_label))`; покрытие на стенде 100 % для 52 почвенных/тканевых (пусть тест
   переноса печатает число непривязанных — ожидается 0; у клиента — число, не догадка).
5. **Старые строки результата анализа** (`zones[]` без `zoneId`) читаются по имени до следующего прогона — одна ветка в
   читателе проекции, снимается стадией 5.
6. **`attributes_json.zones`** после стадии 2 не пишется, после стадии 5 — удаляется из выдачи и валидации
