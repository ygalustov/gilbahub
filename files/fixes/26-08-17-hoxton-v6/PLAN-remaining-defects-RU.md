## Поправки к собственным предпосылкам аудита

Два вывода поменяли статус в ходе проверки — вынесены сюда отдельно, потому что план, который планирует уже сделанную работу или работу, отменённую более поздним обоснованным решением, тратит деньги клиента впустую.

**Атрибуция FoliMAX в D30.** Собственная таблица доказательств аудита по D30 перечисляет "FoliMAX NRG-NK" и "FoliMAX N-Forcer-N" как утечку из "каталога AU", и сам аудит помечает эту атрибуцию как непроверенное воспоминание (см. "Flagged as unverified" в конце исходного документа). `assets/nz-fertiliser-products.js:961-1016` показывает оба продукта под этими же названиями, с `"distributor": "PGG Wrightson Turf"` и `"availability": "NZ National"` — то есть в этой кодовой базе они каталогизированы как NZ-линейка, а не AU. (Одноимённый "FoliMAX NRG-NK" также существует в `assets/au-fertiliser-products.js:2627` как AU-продукт, распространяемый Nuturf, — бренд продаётся разными дистрибьюторами в обеих странах, что, вероятно, и объясняет ошибку атрибуции у клиента.) Это не меняет статус D30 (уже закрыт по другим доказательствам — экспорт читал регион из устаревшего/дефолтного состояния DOM, а не реально протекал настоящим AU-only SKU), но собственную таблицу доказательств клиента не следует повторять как факт в дальнейшей переписке.

**Блок Base Saturation в D25.** Решение аудита просит восстановить весь блок Base Saturation (с Sodium над ним), потому что "удаление было неверным фиксом". Текущий код показывает, что блок **не был удалён** — он существует целиком, включая строку `Sodium (Na)` (`assets/word-export.js:11339-11356`), — но сейчас намеренно подавляется **именно для образцов методологии Ammonium Acetate** (`word-export.js:11337`, `suppressBaseSaturation = methodology === 'AMMONIUM_ACETATE'`), согласно более позднему, процитированному фиксу (`b35fix438`/`b35fix439`, блок комментариев в `word-export.js:11304-11336`), аргументирующему, что %BS/BCSR "не валидирован для газонной травы" (Kopittke & Menzies 2007, *SSSAJ* 71:259-265), и что Carrow, Waddington & Rieke (2001) — те же авторы, которых цитирует сам клиент — рекомендуют интерпретацию по уровню достаточности (SLAN/MLSN) вместо BCSR для газона. Лабораторный набор Hoxton — Ammonium Acetate (Hill Labs NZ), так что это подавление — ровно то, что видел читатель E3. Это тот же самый аргумент, который клиент сам, независимо, приводит в v5.2, убирая свою же цитату Carrow из D07 ("Carrow, Waddington & Rieke критикуют BCSR, а не выступают за него"). См. Решение 2 ниже — это не просто "восстановить", нужно решение клиента с учётом его же заявленного скепсиса к BCSR в другом месте этого документа.

> Olsen P soil 40 mg/L. The export's own Glossary states the typical adequate range for turf is 12 to 28 mg/L. Tissue P 0.62%, flagged above optimal by the export itself. P requirement nonetheless prints at 18.0 kg/ha in E3, and the Prebbles UI schedules MAP Tech in March.

>

**Что код реально делает сегодня.** Проверка по потолку, которую просит клиент, **уже реализована, и уже универсальна по нутриентам, а не только для K**, в обоих движках:

- `assets/nutrition-calendar.js:1537-1542` — `['P', 'K', 'Ca', 'Mg', 'S'].forEach(nutrient => { if (range.max && soilPpm[nutrient] >= range.max) annualRequirements[nutrient] = 0; })`.
- `assets/nutrition-requirement-engine.js:387-401` — проверка потолка в AA-ветке внутри `calculateNutrientRequirement(nutrient, currentLevel, config)` написана универсально по аргументу `nutrient`, а не захардкожена под K.
- Диапазон P резолвится через тот же Olsen-калиброванный источник, что использует лабораторный набор Hoxton: `assets/hill-labs-sample-types.js:83` (`P: {min:20, max:30, unit:'mg/L', extractant:'Olsen'}` для семейства S277) с фолбэком на `assets/ammonium-acetate-methodology.js:83-93`. При Olsen P 40, `40 >= 30` (или `>= 28` по собственной цифре глоссария экспорта) — потолок срабатывает при любом источнике.

**Статус: похоже, уже исправлено как побочный эффект работы по D07, при условии живой проверки.** Собственная регрессионная фикстура клиента уже требует именно эту проверку (утверждение 19: "то же утверждение для P и S, симметрично"). Это **не следует переделывать заново**; это следует **проверить вживую** на фикстуре Hoxton, и если баг воспроизведётся — рассматривать как однострочную регрессию (скорее всего, `HillLabsSampleTypes.deriveCode()` не резолвит диапазон P для этой конкретной комбинации типа образца/вида и падает на неограниченный дефолт — то же "плавное деградирование до неограниченного поведения при отсутствии совпадения по сертификату", задокументированное в GH-300).

**Трудоёмкость:** только проверка (прогнать экспорт на фикстуре Hoxton, подтвердить P req = 0), если живая проверка не провалится — в этом случае это баг разрешения диапазона в `deriveCode()` того же рода, что GH-364 уже чинил для текстуры почвы. ### D01 — ЗАКРЫТО GH-371. Расходящиеся значения GP на разных поверхностях в одном документе, S2, Tier A (был Tier B)

> **Reframed.** ... The operator changed the site coordinates between E2 and E3. The Monthly N Distribution picked the change up. The Monthly Schedule did not, and still renders the pre-correction series byte-identical to E2's. ... So the divergence is not two bindings reading different data, it is one binding plus a cached or persisted copy that survives a site-record write.
>
> **Proof that the UI shares the stale copy.** [таблица перенормировки за девять месяцев, UI совпадает с устаревшей серией с точностью до 0.3 кг]

**Что код реально делает сегодня.** Живой производитель данных правильно ключуется по координатам, и он не проблема: `assets/climate-normals-service.js:174-202` кэширует по `lat.toFixed(2)+','+lon.toFixed(2)` — смена координат даёт другой ключ кэша. Устаревшая копия — это **материализованный, сохранённый объект программы**, а не сам производитель климатических данных:

- `assets/nutrition-calendar.js:1786-1787` — каждый результат `computeProgram()` отправляется на сохранение через `persistSiteConfigPatch({ nutritionCalendarProgram: program, ... })`.
- `assets/site-config-persistence.js:543-551` — блок carry-forward в `snapshotConfig()` копирует `nutritionProgram`/`nutritionCalendarProgram` из существующего конфига вперёд при **каждом** сохранении, безусловно, без проверки, изменилась ли локация сайта с момента последнего расчёта программы.
- `assets/site-config-persistence.js:571-597` — `restoreConfig()` записывает этот блоб напрямую в `window.GAIP_NUTRITION_CALENDAR_PROGRAM` при каждой загрузке страницы.
- `assets/nutrition-calendar.js:2189-2256` — `restoreFromPersisted()` рендерит его через `this.renderResults()` (строка 2235) **без пересчёта против текущего климата** и вызывает `gaip:nutrition-calendar-generated`, как будто это свежий расчёт.
- Именно это событие слушает Prebbles UI (`assets/nutrition-prebble-integration.js:53-64`), поэтому он не может отличить свежую генерацию от устаревшего восстановления и заново сохраняет тот же устаревший результат (`nutrition-prebble-integration.js:371-380`).
- `assets/word-export.js:9724-9744` читает `window.GAIP_NUTRITION_PROGRAM` для Monthly Schedule; защищается от устаревания между *сайтами* (`progSiteId !== currentSiteId`), но не проверяет "посчитано до или после текущих координат".

**Проблема, точно.** Запись координат не инвалидирует ничего. В памяти это переживает мягкую перезагрузку (`nutrition-calendar.js:2205-2208`, `if (this.program) return`); в сохранённом виде переживает жёсткий рефреш. Это соответствует утверждению клиента 13 (запись координат должна инвалидировать каждую закэшированную климатическую серию) и утверждению 1 (все поверхности GP согласуются для данного месяца/семантики).

**Предложенные решения.**
1. **(Рекомендовано.) Проштамповать сохранённую программу координатами, на которых она посчитана, и инвалидировать при несовпадении.** В `computeProgram()` сохранять `{lat, lon}` (уже разрешены, дёшево) вместе с `program`. В `restoreFromPersisted()` и в шаге carry-forward `snapshotConfig()` сравнивать сохранённые координаты с текущими координатами сайта; при несовпадении — выбрасывать закэшированную программу и заставлять живой пересчёт (либо рендерить состояние "нет программы, пересчитайте", которое GH-245 уже построил для случая недоступности климата). ### D41 — UI применяет гарантированный анализ к объёму без конвертации по плотности/SG, S2, Tier A

> The guaranteed analysis on a liquid fertiliser is % w/w. ... So volume must be multiplied by SG before the analysis is applied. The export does this. The UI does not.
>
> | | UI prints | Correct at SG 1.24 |
> |---|---|---|
> | 150 L/ha, (QR) row | 33.0 kg N | **40.9** |
> | 150 L/ha, (Balance) row | 33.0 kg N | **40.9** |
> | 300 L/ha combined | 66.0 kg N | **81.8** |

**Поправка к предпосылке аудита.** Решение аудита v5 утверждает, что экспорт корректно обрабатывает плотность и неверен только UI. **Это больше не соответствует текущему коду — ни одна из поверхностей не применяет конвертацию по плотности.** Поиск по всему репозиторию использования `.density` (`grep -n "\.density\b" assets/*.js`) даёт **ноль совпадений** где-либо, включая `word-export.js` и `word-export-combined.js`. Единственное поле `density`, существующее в каком-либо каталоге продуктов (`assets/prebbles-products.js:798`, `1.34 kg/L` на несвязанном продукте "XXTRA Liquid Iron"), — мёртвые данные, их никто не читает. У самого Ammos 22 поля `density` вообще нет (`prebbles-products.js:804-814`). Наивный расчёт N в UI подтверждён ровно в тех строках, которые цитирует аудит: `prebbles-products.js:1367-1368` (зимняя листовая подкормка: `nDelivered = rateLHa * (analysis.N/100)`, без плотности) и `prebbles-products.js:2204-2209` (строка "(Balance)": `rateLHa = nForThisApp / 0.22`, снова без члена плотности) — это точно воспроизводит цифру аудита 33.0 кг N (30 L/ha × 0.22 × ... ≈ 6.6/применение). Экспорт потребляет те же самые предвычисленные значения `totalKg`/`nutrients.N` из того же модуля продуктов — отдельного шага с учётом SG ниже по потоку тоже нет ни в одном из файлов экспорта.

**Проблема, точно.** Либо доказательства аудита по документам продуктов для пути экспорта (P1/P2, подразумеваемый SG 1.333/1.35) были проверены на более старой сборке, которая больше не соответствует текущему коду, либо цифры "экспорт применяет SG", которые наблюдал аудит, пришли из какого-то другого, с тех пор удалённого пути кода. В любом случае **фикс должен добавить плотность к обеим поверхностям, а не скопировать её с одной на другую** — это меняет форму фикса с "перенести правильную логику экспорта в UI" на "добавить конвертацию в общий код потребления продуктов, поскольку ни у экспорта, ни у текущего UI её нет". Соответствует утверждению 26 (Ammos 22 при 300 L/ha должен вернуть 81.8 кг N, а не 66.0) и утверждению 21 (продукты, указанные в объёме, печатают единицу и SG).

**Предложенные решения.**
1. **(Рекомендовано.) Добавить `density` (кг/л) в схему продукта и заполнить её для каждого жидкого продукта с этикетки, затем применить в единственной точке, где происходит конвертация L→kg.** Каждая этикетка Growth Products несёт вес на литр в одной и той же позиции (по собственной заметке клиента), так что это ввод данных, а не исследование, для этого бренда; каталогам других брендов нужно то же поле, взятое с их собственных этикеток (помечать, а не угадывать, любой продукт, для которого его не найти — то же правило "никаких выдуманных чисел", что и везде в этой кодовой базе). Конкретно для Ammos 22: `density: 1.24 // kg/L, этикетка P1`.
2. Вычислять подразумеваемый SG централизованно, один раз, из `analysis.N%` и задокументированного допущения %w/w-в-w/v, без поля на каждый продукт — отклонено: это ровно тот тип выдуманного коэффициента конвертации, который правило проекта запрещает, когда реальное, взятое с этикетки число уже предоставлено клиентом (P1/P2).

**Трудоёмкость и радиус поражения.** Добавление в схему (поле плотности, дёшево — см. примечание D33 об общей схеме ниже, это должно попасть в **тот же** проход миграции/ввода данных, что и D33, и сужение по вторичным нутриентам D44) + одна общая функция конвертации, используемая как калькуляторами ставок `prebbles-products.js`, так и любым эквивалентным файлом интеграции AU/UK/NZ, делающим ту же математику L→kg (`nutrition-au-fertiliser-integration.js`, `nutrition-nz-fertiliser-integration.js`, `nutrition-uk-fertiliser-integration.js` — подтвердить, что у каждого есть эквивалентная наивная конвертация, прежде чем оценивать полный радиус поражения). Риск регрессии: **каждая существующая цифра N/K/S по жидким продуктам в каждом экспорте изменится** после применения плотности (один только Ammos сдвигается примерно на 24% по N) — это должно выпускаться с явного согласия клиента, что это изменение значения, а не просто фикс отображения, поскольку это меняет то, что Fertiliser Purchasing Summary сообщает поставщику о поставке. **Тест:** утверждение 26 точно как формулирует клиент; также добавить проверку в стиле паритета UI-и-экспорт утверждения 20 специально для доставленного N из объёма.

### D40 — окна переноса оставляют январь и ноябрь непокрытыми, S1, Tier A

> The carry-forward logic works in three-month blocks and drops months that fall outside a block.

**Что код реально делает сегодня.** Подтверждено точным механизмом, а не только симптомом: `assets/prebbles-products.js:1688` строит фиксированный 12-слотовый массив `coveredMonths` (Jan=0…Dec=11); `prebbles-products.js:1882`, `windowMonths = 2` — это **захардкоженное** упреждение "консервативно: считаем, что продукт покрывает ~2 месяца" — текущий месяц + 2 = трёхмесячный блок клиента, применяемый одинаково независимо от того, что реальные данные о продолжительности высвобождения (`releaseWeeks`, см. 1. **(Рекомендовано, соответствует форме фикса клиента.) **Трудоёмкость и радиус поражения:** ограничено блоком переноса `prebbles-products.js` (~строки 1688-1990); подтвердить, дублируют ли независимо файлы региональных интеграций AU/UK/NZ ту же логику фиксированного окна (их собственный код покрытия следует проверить на `windowMonths`, прежде чем считать это специфичным только для Prebbles). Риск регрессии: меняет ровно то, какие месяцы получают "Covered by" против свежего применения, что меняет количество применений продукта в Monthly Schedule — нужен тест паритета (утверждение 25) как жёсткий гейт.

**Трудоёмкость и радиус поражения:** функции выбора жидкостей в `prebbles-products.js` (`selectFoliarNitrogen` и что бы ещё ни итерировало `PrebbleProducts.liquid`, предполагая `form==='liquid'`⇒литры) плюс эвристика `nutrition-prebble-integration.js:1024` (удалить, как только вышестоящий фикс сделает её ненужной). 1. **(Рекомендовано.) Инжектировать SHA деплоящегося git-коммита.** Этот репозиторий деплоится покоммитно через GitHub (согласно собственному CLAUDE.md проекта), так что `git rev-parse --short HEAD` во время деплоя/загрузки — естественный, всегда доступный идентификатор с нулевой неоднозначностью о том, какая сборка произвела данный экспорт — `gilbahub` сам является git-репозиторием с реальной историей коммитов (`HEAD` сейчас `c3b5b57c`), так что SHA доступен в среде деплоя уже сегодня, просто никогда не проявляется. **Трудоёмкость и радиус поражения:** изменение пайплайна деплоя (разрешить и раскрыть SHA — согласовать с тем, кто владеет конфигом GitHub Actions/деплоя) плюс однострочная blade-инъекция, а существующий путь чтения `export-metadata.js` уже работает, как только глобальная переменная установлена. ### D22 — Dew Prediction ограничивает доверие на экспорте, исключающем погоду, S3, Tier A

### D15 — предупреждение о почвенном антагонизме Fe:Mn противоречит ткани Mn, S2, Tier B

> Where tissue data exists for an element, the tissue measurement governs. Suppress the soil-derived antagonism narrative for that element.

**Что код реально делает сегодня.** `mulders-interaction-checker.js:152-330` — правило Fe:Mn (порог 2.5, тяжёлое при 5.0, совпадает с цифрами аудита точно) вычисляется чисто из значений на основе почвы; данные ткани нигде не читаются в `checkMuldersInteractions()` или её вызывающей функции. Предупреждение срабатывает и печатается безусловно, когда почвенное соотношение пересекает порог, независимо от того, что показывает ткань Mn — на Hoxton ткань Mn (189 ppm, 2.6× верхней границы своего диапазона) напрямую противоречит почвенному прогнозу "Mn подавлен".

**Предложенное решение (инженерное решение, агрономический принцип уже установлен собственными цитируемыми доказательствами клиента).** Прокинуть данные ткани в аргумент `context` `checkMuldersInteractions()` (сейчас вообще не передаётся), и когда данные ткани существуют для подавляемого элемента, либо подавить почвенное повествование об антагонизме, либо понизить его до условного примечания ("почвенная химия предсказывает подавление Mn; измерение ткани этого не подтверждает") — собственная форма фикса клиента предлагает оба варианта, а эмпирический случай, который он цитирует (197 парных образцов почвы/ткани, только N и Cu показывают какую-либо корреляцию), поддерживает понижение широко, не только для этой одной пары элементов. Рекомендуется вариант понижения-до-условного-примечания вместо полного подавления — он сохраняет видимой почвенно-химическую логику (полезный контекст), делая при этом ясным, что она не подтвердилась, вместо удаления информации, которую читатель всё ещё может хотеть.

**Трудоёмкость и радиус поражения:** сигнатура функции `mulders-interaction-checker.js` и её точка(и) вызова нуждаются в прокладке данных ткани — проверить, сколько точек вызова существует и надёжно ли доступны данные ткани во всех них до этого вызова (порядок вычисления важен: анализ ткани должен запуститься до проверщика взаимодействий, иначе это станет собственным крайним случаем "ткань ещё не доступна"). Умеренная трудоёмкость с учётом прокладки, низкий вычислительный риск. **Тест:** на фикстуре с противоречащими доказательствами почва-против-ткани Fe:Mn (как Hoxton), утвердить, что повествование об антагонизме понижено/условно, а не заявлено как факт.

**Зависимости:** нет блокирующих, но затрагивает тот же файл проверщика взаимодействий, на который ссылаются комментарии об отмене BCSR Ca:Mg D08 (`b35fix439`/`b35fix440`) — прочитать эту историю перед редактированием, в файле уже есть недавние, тщательно процитированные изменения.

### D24 — окно вмешательства инверсно композиту, доминируемому траффиком, без прогнозных данных, S1, Tier B

> The gate should be two-factor: growth potential at or above 50% AND daily light integral at or above the species-and-height recovery threshold. Either one below floor returns an empty window naming the limiting factor.

**Что код реально делает сегодня.** Подтверждено с точным механизмом. Композит ("ESI") вычисляется в `stress-trajectory-engine-pure.js` с весами `{thermal:0.20, light:0.15, moisture:0.20, traffic:0.20, nutrition:0.15, biotic:0.10}` (~строки 97-107) — воспроизводя цифру аудита `100×0.20 + 0.7×0.20 = 20.14` точно. Само окно вмешательства (`stress-trajectory-engine-pure.js:891-916`) построено **исключительно** из `trajectory[i].totalScore < CONFIG.thresholds.normal` — ни GP, ни DLI нигде в этом цикле или окружающей функции; `grep` по `GrowthPotential`/`growth-potential` в этом файле ничего не даёт. Константы порога GP какого-либо рода нигде сейчас не существует в файлах stress-trajectory (подтверждено отсутствие). Отдельно, термический стресс (`stress-trajectory-engine-pure.js:187-266`, кусочно-линейная рампа от `{min:15,max:24,peak:20}`) и growth potential (`growth-potential-engine.js:38-56`, гауссиан PACE, `optimum:20, sigma:5.5`) — две структурно независимые модели температуры (это D38, то же самое сопряжение файлов, включено сюда, поскольку это механизм, на котором реально работает термический компонент D24) с нулевой перекрёстной ссылкой в любом направлении.

**Рекомендация, которую окно вмешательства должно консультировать, уже существует и уже корректна**, подтверждена в `assets/growth-light-analysis.js:1850-1851` (функция `gpRec`): `if (gp < 40) { ... 'growth potential critically low (' + fmt(gp,0) + '%). Defer aggressive cultural practices — focus on stress recovery.' }` — это "хаб уже держит правильное правило", на которое ссылается клиент; это другой модуль (`growth-light-analysis.js`, питающий панель Recommendations), который движок stress-trajectory просто никогда не вызывает. **Важно: это существующее правило срабатывает при `gp < 40`, не установленном клиентом пороге 50%** — фикс D24 должен ввести собственную именованную константу `CULTIVATION_GP_FLOOR = 0.50` согласно решению клиента v5.1, не копировать порог `40` этого модуля, который отвечает на связанный, но другой вопрос (когда сайт находится под критическим стрессом вообще), а не на вопрос пригодности к культивации, которым занимается D24. Никакой именованной константы порога GP какого-либо рода сейчас нигде не существует в кодовой базе (подтверждено отсутствие grep'ом) — это будет новая константа в любом случае.

**Механизм затухания, в закрытой форме.** Таблица весов `stress-trajectory-engine-pure.js` (~строки 95-113) сопрягает каждый компонент с собственным `recoveryDays` (`thermal:7, light:10, moisture:5, traffic:7, nutrition:14, biotic:14`); прогноз вперёд (`stress-trajectory-engine-pure.js:798-836`) затухает каждый непрогнозированный компонент как `current × (1 − 1/recoveryDays)^n`. Поскольку композит нулевого дня Hoxton — это только thermal(0.7)+traffic(100), и оба случайно разделяют `recoveryDays=7`, вся траектория сводится к единой экспоненте `20.14 × (6/7)ⁿ` (база 0.857), чрезвычайно близкой, но не побитово идентичной подогнанной клиентом `20×0.851ⁿ` — тот же механизм (снимок нулевого дня, затухший без прогнозных данных, принятый за прогноз), небольшой разрыв в базовой ставке, скорее всего, объясняется округлением отображения `Math.round`/`ceil`, накапливающимся за 14 шагов, либо реальными температурами прогноза, подставляемыми вместо затухания в дни, когда они доступны (`stress-trajectory-engine-pure.js:801-808` ветвится на данные прогноза, когда они присутствуют). Подтверждает предпосылку утверждения 23 напрямую: это сфабрикованное однопараметрическое затухание, а не реальный 14-дневный прогноз.

**Предложенное решение (агрономический параметр уже установлен клиентом — порог GP 50%, решение v5.1; порог DLI нуждается в том, чтобы сначала существовала таблица вид/высота D48).**
1. Добавить gate по порогу GP в цикл построения окна `stress-trajectory-engine-pure.js` (~строка 891): перед добавлением интервала в `interventionWindows`, дополнительно требовать, чтобы текущий GP сайта был ≥ новая именованная константа (`CULTIVATION_GP_FLOOR = 0.50`), и когда он ниже порога, возвращать пустое окно со строкой причины ограничивающего фактора, согласно форме фикса клиента.
2. Добавить gate по DLI таким же образом, один раз — **но только когда D48 произведёт реальную таблицу порогов вид/высота** (см. D48 ниже); до этого эта половина не может быть реализована без изобретения числа, что противоречит правилу проекта. Приземлить GP-gate первым как собственное изменение (оно независимо ценно и разблокировано сегодня), DLI-gate как последующее, как только D48 приземлится.
3. **Этот же фикс следует реализовать на уровне общего композита/gate**, не дублировать по-поверхностно — и D46 (Component Breakdown), и D47 (баннер "Conditions favorable") читают из того же объекта `trajectory`/`peakScore`, из которого построено это окно; gate на общем источнике означает, что все три поверхности (окно, разбивка, баннер) плюс карточка Wear Resistance, которую клиент отдельно флагирует, становятся согласованными в одном изменении, соответствуя собственной инструкции клиента, что исправление одного D24 "оставляет две из четырёх поверхностей всё ещё противоречащими пятой".

**Второй, меньший фикс (тоже D24, согласно аудиту): 14-дневная траектория затухает единственное известное значение (сегодняшний traffic=100) до нуля без прогнозных данных, и затухание читается модулем как "улучшение".** Согласно форме фикса клиента: удерживать последнее известное значение, либо убрать беспрогнозный компонент из взвешивания и перенормировать, либо усечь горизонт прогноза до реально доступных данных — не затухать до нуля и называть это улучшением. Рекомендуется усечение горизонта прогноза (проще всего, наиболее честно — сама логика окна не должна отображать или гейтовать по дням, для которых у неё нет реальных данных) вместо удержания-последнего-значения (которое рискует выглядеть как реальный прогноз, когда это не так) или перенормировки (добавляет сложность за незначительное преимущество над усечением).

**Трудоёмкость и радиус поражения:** основной gate — умеренное, хорошо ограниченное добавление в одну функцию `stress-trajectory-engine-pure.js`; часть "тот же фикс достигает D46/D47/Wear Resistance" означает, что нижестоящим рендерерам нужно читать скорректированное значение вместо сырого композита, что более крупное, но механическое продолжение, как только источник исправлен. Это самый ценный элемент, кроме D30, в этом списке согласно собственному ранжированию серьёзности клиента (S1) и его же замечанию, что маршрутизация Tier B WordPress-плагина больше не применяется — сильный кандидат на это понижение, поскольку это дешевле в SaaS, чем подразумевала исходная метка.

**Тест:** утверждение 22 точно (пустое окно ниже порога GP 50%, с напечатанной причиной, на фикстуре Hoxton, где GP 10-26%); утверждение 23 (траектория стресса не должна быть воспроизводима однопараметрической подгонкой затухания по всей своей длине — это напрямую тестирует фикс "удержать/усечь/перенормировать").

**Зависимости:** половина GP-gate может приземлиться независимо; половина DLI зависит от D48; согласованность D46/D47/карточки Wear Resistance должна приземлиться в том же изменении, что и основной gate, не как отдельный последующий проход.

### D31 — ЧАСТИЧНО: баг единиц закрыт GH-370, этап 1 объединения GH-376, переключение движков впереди. UI и экспорт вычисляют требования K/P разными методами; баг единиц ppm→kg/ha, S2, Tier B

> The UI derives K and P as fixed ratios off the monthly N series (D07a). The export derives them from removal-replacement in the requirements engine. The two land 10% apart on the same site.

**Что код реально делает сегодня.** Два по-настоящему разных метода, теперь сошедшихся по вопросу tissue-gate (GH-361/368 оба применяют одно и то же правило tissue-ratio-когда-доступен), но всё ещё структурно разных в том, против чего они масштабируют это соотношение: `nutrition-calendar.js` масштабирует соотношение ткани/общее против реальной цели `annualN` сайта (`nutrition-calendar.js:1317-1318`, `Math.round(annualN * _pRatio)`); `nutrition-requirement-engine.js` масштабирует его против **фиксированной константы N таблицы вида** (`nutrition-requirement-engine.js:195`, `table.N * ratio`, `table.N = 180` для perennial ryegrass) — так что если реальная цель годового N сайта (например, 200 у Hoxton) отличается от статичных 180 таблицы, два движка всё равно приземлятся на разные цифры P/K даже с идентичными данными ткани. Также структурно разные модели скашивания — `nutrition-calendar.js:139-151` (`collected: nFactor 1.0, pFactor 1.0, kFactor 1.0`; `returned: nFactor 1.0, pFactor 0.4, kFactor 0.5`) против `nutrition-requirement-engine.js:216-219,604` (`CLIPPING_COLLECTION_FACTOR = 2.5`, `returned` фактически 1.0×) — и разные модификаторы траффика (`nutrition-calendar.js:155`, `{low:0.85, moderate:1.0, high:1.15, extreme:1.3}` против `nutrition-requirement-engine.js:223`, `{low:0.8, moderate:1.0, high:1.2, extreme:1.5}`).

**Подтверждён, независимо, ровно как подозревалось: баг единиц ppm→kg/ha.** В `nutrition-requirement-engine.js` **ноль** вхождений `bulkDensity`, `soilDepth` или коэффициента конвертации `* 0.1` где-либо в файле. Каждый член коррекции во всех трёх ветках методологии вычисляет сырую ppm-дельту, делённую на годы, и добавляет её напрямую к цифре выноса в kg/ha без размерной конвертации:
- AA: `nutrition-requirement-engine.js:404`, `const aaCorrection = (aaRange.min - currentLevel) / yearsToCorrect;` → `:412`, `annualRequirement: Math.round((removal + aaCorrection) * 10) / 10`.
- SLAN: `:578`, `slanCorrection = (rangeFloor - currentLevel) / yearsToCorrect;`.
- MLSN: `:607`, `const correctionRequired = currentLevel < threshold ? (target - currentLevel) / yearsToCorrect : 0;`.

`nutrition-calendar.js` делает конвертацию корректно, дважды — `calculateDeficit()` (`:1008-1009`, `const kgHa = deficit * bulkDensity * soilDepth * 0.1;`) и инлайново (`:1497`, `(floor - currentPpm) * inputs.bulkDensity * inputs.soilDepth * 0.1`). И критически, **сырые неограниченные цифры GDD уже печатаются на той же карточке**, без ограничения, прямо рядом с ограниченным процентом: `plan-ui.js:809-810,816`, `pgrAccum + ' / ' + pgrThresh + ' GDD'` (541/350, совпадает с собственной скорректированной цифрой аудита точно) — так что исходные данные для вычисления перерасхода 155%/191-GDD уже видны на карточке, просто не предвычислены в заголовочный процент.

**Предложенные решения.**
1. **GP-gate (согласованная форма фикса, агрономический параметр уже установлен — тот же порог 50%, что D24).** Добавить тот же gate `CULTIVATION_GP_FLOOR`, который D24 вводит, в тернарный оператор статуса реаппликации, точнее — подавлять состояние бейджа "apply now"/"overdue" конкретно (не лежащее в основе отслеживание GDD, которое должно продолжать работать), когда GP ниже порога, соответствуя форме фикса клиента ("гейтовать реаппликацию PGR на том же пороге GP, что D24"). Переиспользовать именованную константу D24 вместо дублирования.
2. **Отображение прогресса, инженерное решение (не агрономическое).** Учитывая, что сырые цифры GDD уже видны, есть два реальных варианта: (a) снять ограничение с самого процента (показывать "155%"), что меняет визуальный вес пары номер/бейдж, вокруг которой был спроектирован намеренный потолок (собственное обоснование комментария кода — "бейдж сообщает состояние просрочки" — нужно было бы переоценить, если процент тоже снимет ограничение, поскольку тогда и число, и бейдж говорят одно и то же, что может быть желательным или может быть избыточным); либо (b) держать процент ограниченным точно как спроектировано, но добавить явную строку "191 GDD over" или "55% over threshold" рядом с ним, удовлетворяя реальную претензию клиента (скрывает степень перерасхода) без изменения существующего дизайна ограниченный-процент-плюс-бейдж. Рекомендуется (b) — это аддитивно, сохраняет рабочий, намеренный дизайнерский выбор, и напрямую отвечает на то, что клиент реально просит (видимость масштаба перерасхода, не обязательно неограниченное число).

**Трудоёмкость и радиус поражения:** (1) небольшая, разделяет константу с D24 (оформить последовательно или сразу после). (2b) небольшое добавление к той же карточке. Низкий риск регрессии для обоих — (1) только подавляет состояние бейджа при новом условии, (2b) только добавляет текст.

**Тест:** утверждение 24 точно (реаппликация PGR не срабатывает ниже порога GP 50%).

## Технические открытые вопросы

Не из аудита клиента — найдены нами по ходу работы. Это единственный список: отдельный файл `REVIEW-GH349-onward.md`, где они жили раньше, удалён, а его содержательная часть перенесена сюда.

**1. Устаревший браузер удаляет лабораторные образцы, добавленные с другого устройства.** Самое серьёзное из найденного. `POST /api/samples/sync` работает не как «добавь эти образцы», а как «вот моя полная картина, приведи базу в соответствие»: всё, чего нет в присланном снимке, сервер удаляет. Источником истины считается localStorage браузера. Сценарий: в браузере A образцы 1-3, с браузера B импортируют образец 4, браузер A синхронизируется и образец 4 удаляется. Срабатывает не только при импорте, а на любом изменении и **даже на переключении сайта** — то есть достаточно старой открытой вкладки. Наследие плагинной архитектуры, где localStorage был единственным хранилищем. Тот же механизм в более мягкой форме затрагивает конфиги сайтов (там теряется настройка, а не данные). Разобрано по коду, вживую не воспроизводилось. Правильное решение — перестать слать снимок целиком и мержить по записям с отметкой времени; копировать модель образцов на конфиги нельзя, она сама и есть проблема.

**2. Достижимость: реальность зависит от того, работаете ли вы с нескольких мест.** Пункт выше наступает только если существуют две сессии, где одна устарела — два браузера, браузер и телефон, или одна забытая открытая вкладка. Если работа всегда идёт с одного места, сценарий не реализуется. Это стоит определить прежде, чем оценивать приоритет.

**3. Программа не сбрасывается при смене расчётных входов, кроме координат и вида травы.** GH-371 сравнивает координаты, GH-377 — вид травы и методологию. Но `computeProgram()` зависит и от других входов, изменение которых сохранённую программу не трогает. Не воспроизведено на конкретном поле; риск в том, что пользователь меняет настройку и продолжает видеть цифры, посчитанные до неё.

**4. Программа без штампа координат молча заменяется более старой со штампом.** В `SiteController::resolveGaipConfigWrite()` программа без штампа не проходит проверку доверия и отбрасывается. Достижимость под вопросом: живой запрос показал, что программ без штампа в базе нет. Держим в списке, пока не докажем обратное.

**5. Одиночный экспорт недостижим из нового хаба.** Любой экспорт с `/reports/export` идёт через комбинированный конвейер, сколько бы образцов ни было выбрано. Ветка одиночного экспорта в `word-export.js` живёт, покрыта тестами, но проверить её вживую из нового хаба нельзя — только из старого. Из-за этого пометку «цель N взята из настроек» в одиночном отчёте (GH-388) подтвердили тестом, но не глазами.

**6. На Burns не печатается раздел сверки калия.** После GH-387 программа на этом поле калий не даёт, механизм видит ноль доставки и убирает раздел целиком. По своей логике верно, но клиент не видит ни слова про калий на поле, где калия в почве 195 ppm при потолке 55.5. Нужно продуктовое решение: показывать раздел с нулём и объяснением или оставить как есть. Отложено самим пользователем в хвост 10.09.2026.

**Закрыты по ходу как нереальные сценарии:** паразитная секция «климат недоступен» у сайта без координат (сайт без координат не работоспособен в принципе — нет ни GP, ни программы, ни рисков болезней), и тихая подмена непроштампованной программы (достижима только в том же состоянии). Оба разобраны и задокументированы с доказательствами на случай, если предпосылка изменится.

8. **D05 → D44 — расширение сверки.** Ждало объединения движков, чтобы циклы нутриентов пришлось тронуть один раз, а не дважды по двум движкам. Теперь разблокировано. ~2-3 дня.
9. **D13b / D24 / D48 — общий контракт модели вердикта, согласно собственной группировке клиента.** Построить контракт четвёртого состояния вердикта один раз (Решение 5), затем: gate по порогу GP D24 первым (разблокирован, агрономический параметр уже установлен, наивысшая серьёзность из трёх) с согласованностью D46/D47/карточки Wear Resistance в том же изменении; таблица вид-по-высоте D48, как только будут отвечены Решения 6/7; тегирование качества диапазона ткани D13b может приземлиться независимо от любого из них, тот же контракт. Это второй по величине оставшийся кусок инженерной работы — рекомендуется 1.5-2 недели на весь кластер, с основным gate D24, поставляемым в первые несколько дней этого окна, поскольку он независимо ценен и наименее заблокирован.
10. **D32 — gate PGR + раскрытие перерасхода.** Небольшой, переиспользует константу порога GP D24 — приземлить сразу после того, как gate D24 существует, а не как отдельный слот планирования. ~1 день.
11. **Общее правило D03 — оставшиеся места тихого фолбэка** (климат Event Planner, паттерн-фолбэк прогноза болезней, устаревший путь питания). Независимо от всего остального в этом списке; может выполняться параллельно с любым из вышеперечисленного, как только позволят ресурсы, поскольку не разделяет файлы с другими кластерами. ~2-3 дня по трём местам, каждое независимо тестируемо.
12. **D27 — только перемерить.** Ждало D01 и D31, оба приземлились, так что мерить можно. Отдельного слота сборки нет; задача проверки, а не сборки.

Общая грубая оценка масштаба на сегодня: пакет рендереров Tier A — порядка 3 недель ограниченной, в основном независимой работы; контракт модели вердикта D13b/D24/D48 — единственный оставшийся по-настоящему инженерный кусок, 1.5-2 недели; добавление схемы D33 стоит сделать рано, поскольку из него потребляют D41 и D44. Ничто в этом списке не заблокировано ничем вне его — никакое ограничение WordPress-плагина не применяется, что согласуется с собственным переосмыслением v6 клиента. Единственное, что стоит перед всем перечисленным по серьёзности, а не по последовательности — удаление образцов при синхронизации (пункт 2).
