## Build order 3 of 4 — the stale climate copy (D01, D01a, D02a)

### D01 — divergent GP values across surfaces in one document, S2, Tier A (was Tier B)

> **Reframed.** ... The operator changed the site coordinates between E2 and E3. The Monthly N Distribution picked the change up. The Monthly Schedule did not, and still renders the pre-correction series byte-identical to E2's. ... So the divergence is not two bindings reading different data, it is one binding plus a cached or persisted copy that survives a site-record write.
>
> **Proof that the UI shares the stale copy.** [nine-month renormalisation table, UI agrees with the stale series to 0.3 kg]

**What the code actually does today.** The live producer is correctly coordinate-keyed and not the problem: `assets/climate-normals-service.js:174-202` caches by `lat.toFixed(2)+','+lon.toFixed(2)` — a coordinate change produces a different cache key. The stale copy is a **materialised, persisted programme object**, not the climate producer itself:

- `assets/nutrition-calendar.js:1786-1787` — every `computeProgram()` result is pushed to persistence via `persistSiteConfigPatch({ nutritionCalendarProgram: program, ... })`.
- `assets/site-config-persistence.js:543-551` — `snapshotConfig()`'s carry-forward block copies `nutritionProgram`/`nutritionCalendarProgram` from the existing config forward on **every** save, unconditionally, with no check of whether the site's location changed since the program was last computed.
- `assets/site-config-persistence.js:571-597` — `restoreConfig()` writes this blob straight into `window.GAIP_NUTRITION_CALENDAR_PROGRAM` on every page load.
- `assets/nutrition-calendar.js:2189-2256` — `restoreFromPersisted()` renders it via `this.renderResults()` (line 2235) **without recomputing against current climate**, and fires `gaip:nutrition-calendar-generated` as if it were freshly generated.
- That event is what the Prebbles UI listens for (`assets/nutrition-prebble-integration.js:53-64`), so it cannot distinguish a fresh generate from a stale restore, and re-persists the same stale result (`nutrition-prebble-integration.js:371-380`).
- `assets/word-export.js:9724-9744` reads `window.GAIP_NUTRITION_PROGRAM` for the Monthly Schedule; it guards against cross-*site* staleness (`progSiteId !== currentSiteId`) but has no check for "generated before vs. after the current coordinates."

**The problem, precisely.** A coordinate write invalidates nothing. In-memory it survives a soft reload (`nutrition-calendar.js:2205-2208`, `if (this.program) return`); persisted it survives a hard refresh. This maps to the client's assertion 13 (coordinate write must invalidate every cached climate series) and assertion 1 (all GP surfaces agree for a given month/semantic).

**Proposed solutions.**
1. **(Recommended.) Stamp the persisted programme with the coordinates it was computed against, and invalidate on mismatch.** On `computeProgram()`, store `{lat, lon}` (already resolved, cheap) alongside `program`. On `restoreFromPersisted()` and on `snapshotConfig()`'s carry-forward step, compare stored coordinates to the site's current coordinates; on mismatch, drop the cached programme and force a live recompute (or render the "no programme, recompute" state GH-245 already built for the climate-unavailable case). This is an engineering decision with a working precedent already in the codebase: `assets/eue-integration-bridge.js:1271-1284` does exactly this pattern (`_lastClimate = null` + refetch) on a GSSH venue-select event.
2. **Drop persistence of the computed programme entirely and always recompute live from current climate on page load.** Simpler, but changes load-time behaviour (a network/compute round-trip on every page open) and removes an optimisation that may exist for a reason (rate-limiting the climate API). Needs confirmation this optimisation isn't load-bearing before choosing this over option 1.
3. **Server-side invalidation**: have `SiteController::update()` (the lat/long-owning endpoint, `app/app/Http/Controllers/SiteController.php` ~line 162-197) clear the cached programme fields in `SiteConfig` directly when coordinates change, so the client never even receives a stale blob to restore. Belt-and-braces alongside option 1, not a replacement — client-side persistence (localStorage, if any) would still need the client-side check too.

Recommend **1 + 3 together**: stamp-and-check on the client (fast, catches the localStorage/browser-persisted case) plus a server-side clear on the coordinate-write endpoint (catches any other client that reads the stale `SiteConfig` row directly, e.g. a future mobile client or the Word export's own site lookup).

**Effort and blast radius.** All four regional nutrition integrations share the identical `window.GAIP_NUTRITION_PROGRAM = program` + `persistSiteConfigPatch` pattern (`nutrition-au-fertiliser-integration.js:402`, `nutrition-nz-fertiliser-integration.js:380`, `nutrition-uk-fertiliser-integration.js:860`, `nutrition-prebble-integration.js:378-380`) — the stamp-and-check needs to land once in the shared persistence layer (`site-config-persistence.js`), not four times. Also touches `word-export.js:9727-9744` and the equivalent block in `word-export-combined.js`. Regression risk is moderate — this is exactly the kind of change that could introduce a recompute-on-every-load performance regression if done as option 2, or a subtle race if the coordinate comparison uses stale in-memory state; test by asserting (a) the persisted blob is used when coordinates match, (b) a coordinate change forces recompute and all of Monthly Schedule / Monthly N Distribution / UI monthly programme change together, matching assertion 13.

**Test:** new `tests/ghNNN-d01-coordinate-invalidation.test.js` — set coordinates, generate, change coordinates, assert `nutritionCalendarProgram` is either absent or recomputed on next read, and that the Monthly Schedule and Monthly N Distribution numbers match to one decimal (assertion 1).

**The problem, precisely.** Either the audit's product-document evidence for the export path (P1/P2, implied SG 1.333/1.35) was checked against an older build that no longer matches current source, or the "export applies SG" figures the audit observed came from some other, since-removed code path. ### D40 — carry-forward windows leave January and November uncovered, S1, Tier A

> The carry-forward logic works in three-month blocks and drops months that fall outside a block.

**What the code actually does today.** Confirmed with an exact mechanism, not just the symptom: `assets/prebbles-products.js:1688` builds a fixed 12-slot `coveredMonths` array (Jan=0…Dec=11); `prebbles-products.js:1882`, `windowMonths = 2` is a **hardcoded** "conservative: assume product covers ~2 months" lookahead — current month + 2 = the client's three-month block, applied uniformly regardless of what the actual release-duration data (`releaseWeeks`, see D33) says for the product chosen. The coverage-marking loops (`prebbles-products.js:1883`, `:1939`, `:1973`) are all bounded `< 12` / `< monthlyData.length` with **no modulo/wraparound** (`grep -n "% 12"` across the file returns zero matches) — a December application's coverage window can never reach back into January. November's exposure follows from the same fixed 2-month cap starting wherever the last full (non-covered) application landed.

**Proposed solutions.**
1. **(Recommended, matches the client's fix shape.) Replace the fixed 2-month lookahead with a mass-balance-driven window**: extend coverage until the product's own decayed remaining N/K (already computed per month, see the `decayFactor` logic at `prebbles-products.js:1941-1946`) drops below the threshold that currently triggers `isCovered` (`monthData.N * 0.3`, line 1700), rather than stopping at a fixed month count. This naturally extends into January from a December application when the decayed remainder still matters, without inventing a new constant.
2. **Simpler, matches the client's "or" option: emit an explicit uncovered-month flag** wherever a month has a non-zero requirement and neither a scheduled application nor a `coveredBy` entry, and fail the export (or flag it loudly on-screen) rather than silently rendering a dash. Lower engineering risk than option 1, does not fix the underlying gap, only surfaces it — the client's own wording treats these as alternatives ("either... or"), not sequential steps, so this alone would satisfy the letter of the fix shape but leave the actual N delivered short.

Recommend doing **both**: option 1 closes the actual gap (this is what moves the needle on the 59%-of-shortfall figure the client computed), option 2 is the safety net for whatever residual gap remains after a real mass-balance model (there will always be some site/product combination that can't be fully covered). This is squarely the client's own instruction: "Fixing this closes roughly 60% of the N gap without touching product selection" — a pure scheduling-window fix, no change to which products get selected.

**Effort and blast radius:** contained to `prebbles-products.js`'s carry-forward block (~lines 1688-1990); confirm whether the AU/UK/NZ regional integration files have independently duplicated the same fixed-window logic (their own coverage code should be grepped for `windowMonths` before treating this as Prebbles-only). Regression risk: changes exactly which months get "Covered by" vs a fresh application, which changes the Monthly Schedule's product-application count — needs the parity test (assertion 25) as a hard gate.

**Test:** assertion 25 exactly ("every month with a non-zero nutrient requirement has either a scheduled product or an explicit covered-by reference; an uncovered month with a requirement fails"). Re-run against the corrected D41 density figures once both land, since D41 changes how much N a covering application actually delivered.

### D42 — Lo Biuret Urea flips unit between schedule (L) and summary (kg), S2, Tier A

> Fifty of one becomes fifty of the other with no conversion. It is also a soluble solid being scheduled in litres in the first place.

**What the code actually does today.** Root cause fully traced: the product record is correctly modelled as a solid (`prebbles-products.js:1029-1042`, `form: 'soluble'`, `maxRateKgHa: 150`, no `maxRateLHa`) but lives inside the `PrebbleProducts.liquid` array (no separate soluble-solid category exists in the selection pipeline). `selectFoliarNitrogen()` (`prebbles-products.js:3147-3150`) explicitly treats `form === 'soluble'` as a liquid candidate; the rate math (`prebbles-products.js:3311`) is unconditionally litre-based (`rateLHa = N / nPct`), substituting the generic 30 L/ha liquid cap (`prebbles-products.js:3267/3314`, `product.maxRateLHa || 30`) in place of the product's real 150 kg/ha solid cap since `maxRateLHa` is absent; the returned object then force-sets `form: 'liquid'` regardless of the source record (`prebbles-products.js:~3408-3410`). Downstream, the Annual Product Summary separately re-detects "soluble" by a **name-string heuristic** (`nutrition-prebble-integration.js:1024`, `data.name?.includes('soluble')`) and switches the *label* to kg/ha without applying any conversion to the *number* — so the same raw figure (e.g. 50) prints under both an "L/ha" label in the schedule and a "kg/ha" label in the summary.

**Proposed solution.** Give the selection pipeline a real `form === 'soluble'` branch (distinct from `'liquid'`) that carries `rateKgHa` through instead of `rateLHa`, uses `maxRateKgHa` as its cap, and is rendered with a `kg/ha` unit at every surface from the point of computation onward — removing the need for the downstream name-string heuristic entirely. This is the same root cause the client identifies as shared with D08 ("unit is display metadata rather than part of the value") — fixing it here should follow the same "unit travels with the value" principle rather than being patched surface-by-surface.

**Effort and blast radius:** `prebbles-products.js`'s liquid-selection functions (`selectFoliarNitrogen` and whichever else iterates `PrebbleProducts.liquid` assuming `form==='liquid'`⇒litres) plus `nutrition-prebble-integration.js:1024`'s heuristic (delete once the upstream fix makes it unnecessary). Check whether any other soluble-solid product besides Lo Biuret Urea shares this misclassification before scoping (grep `form: 'soluble'` across all product catalogue files). Low regression risk if scoped to solubles only — liquids are untouched.

**Test:** new fixture assertion — a soluble product's Monthly Schedule figure and Annual Product Summary figure must be numerically consistent under a stated unit at both surfaces (extend the audit's own fixture, no assertion number currently covers this specifically — add it).
